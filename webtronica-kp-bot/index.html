1. Назначение прототипа

Прототип демонстрирует Telegram-сценарий запуска создания коммерческого предложения внутри Вебтроники.

  1. Бот по шагам собирает входные настройки.
  2. По выбранному региону автоматически определяет поисковую систему или обе поисковые системы.
  3. Передаёт задачу в Вебтронику.
  4. Показывает статус обработки.
  5. После готовности присылает КП и ссылки на внутренние документы, на основе которых оно было сформировано.

В HTML-версии все интеграции имитируются JavaScript без реальных API-запросов.

2. Общий дизайн и UX
  • Интерфейс имитирует Telegram Desktop и адаптируется под мобильный экран.
  • Сообщения бота расположены слева, пользователя — справа.
  • Используются inline-кнопки, время сообщений, состояние «печатает…» и автоматическая прокрутка.
  • DEV-панель постоянно видна на широком экране и открывается поверх чата на узком.
  • Все действия выполняются без перезагрузки страницы.
3. Актуальная последовательность диалога
  1. Команда «Создать КП».
  2. Ввод URL продвигаемого сайта.
  3. Выбор региона из полного списка регионов Keyso.
  4. Автоматическое определение ПС по выбранному региону.
  5. Ввод обязательных конкурентов одним сообщением либо пропуск шага.
  6. Если обязательные конкуренты указаны — выбор режима их использования. Если шаг пропущен — сразу итоговая проверка.
  7. Итоговая проверка параметров.
  8. Запуск задачи внутри Вебтроники.
  9. Сообщение о принятии задачи.
  10. Автоматическое обновление статуса.
  11. Получение КП и ссылок на внутренние документы Вебтроники.

Удалено из сценария: выбор поисковой системы, отдельная настройка сводного отчёта, ручной ввод региона и шаг «Исключаемые домены».

4. Команда «Создать КП»

Начальное сообщение содержит короткое объяснение и кнопку Создать КП. После клика бот запускает пошаговый сценарий и запрашивает URL сайта.

Кнопка полного сброса в шапке очищает состояние прототипа и возвращает пользователя к начальному экрану.

5. URL продвигаемого сайта

Поле обязательное. Допускаются адреса с протоколом, www и путём: example.ru, https://www.example.ru/catalog/.

  • Проверяется наличие корректного домена и доменной зоны.
  • Запрещаются пробелы и недопустимые символы.
  • Для дальнейшей логики значение нормализуется до домена без www.
  • При ошибке бот предлагает повторный ввод или отмену сценария.
6. Полный список регионов Keyso

После URL бот сразу выводит inline-кнопками весь доступный список регионов Keyso. На самих кнопках показывается только название региона — без упоминания поисковой системы.

Список: Москва, Минск, Нью-Йорк, Киев, Санкт-Петербург, Екатеринбург, Краснодар, Н. Новгород, Ростов-на-Дону, Казань, Омск, Волгоград, Пермь, Новосибирск, Челябинск, Самара, Уфа, Красноярск, Воронеж, Саратов, Тюмень, Томск.

Соответствие регион → ПС остаётся внутренней логикой: Москва и Минск — Яндекс + Google; Нью-Йорк и Киев — Google; остальные регионы — Яндекс.

В рабочей версии список и соответствие регион → ПС рекомендуется получать из Вебтроники/Keyso-конфигурации, чтобы бот не содержал устаревающий справочник.

7. Автоматическое определение поисковых систем

ПС — вычисляемое поле, а не пользовательская настройка.

  • Москва, Минск → ["yandex", "google"].
  • Киев, Нью-Йорк → ["google"].
  • Все остальные регионы из текущего списка → ["yandex"].

После выбора региона бот информационно подтверждает регион и набор ПС. При повторном редактировании региона набор ПС пересчитывается заново.

8. Логика Москвы и Минска

Отдельная настройка «Сводный отчёт по Яндексу и Google» отсутствует.

Выбор Москвы или Минска автоматически включает сбор данных сразу в Яндексе и Google. Пользователь не выполняет дополнительных действий.

9. Ввод обязательных конкурентов

На этом шаге пользователь может указать сайты конкурентов, которые обязательно нужно учесть при анализе. Отправляется один или несколько доменов/URL одним сообщением, каждый конкурент — с новой строки. Шаг необязательный.

  • Каждая строка валидируется отдельно как домен/URL сайта конкурента.
  • Допускаются URL с протоколом, www и путём.
  • Значения нормализуются до домена.
  • Удаляются дубликаты.
  • Запрещено добавлять продвигаемый домен как собственного конкурента.
  • Корректные строки сохраняются, даже если часть списка содержит ошибки.

Важно: при нажатии «Пропустить» бот не отправляет сообщение о пропуске и не показывает выбор режима. Он сразу переходит к итоговой проверке параметров.

10. Режим обязательных конкурентов

Этот шаг показывается только если пользователь указал хотя бы одного обязательного конкурента. Доступны три варианта:

  1. Всегда добавлять в анализ — учитывать указанных конкурентов независимо от наличия в выдаче.
  2. Учитывать только при наличии в выдаче — учитывать обязательного конкурента только если он найден в поисковой выдаче.
  3. Анализировать только указанных конкурентов — автоматический поиск конкурентов не выполняется.

Если список обязательных конкурентов пуст, поле режима должно быть очищено и сам шаг полностью пропускается как в UI, так и в payload для backend.

11. Итоговая проверка и редактирование

Бот показывает карточку со всеми собранными параметрами и кнопками запуска, изменения и отмены.

Отображаются: сайт, регион, автоматически определённые ПС и обязательные конкуренты. Режим обязательных конкурентов отображается только если такие конкуренты указаны.

Раздел «Изменить параметры» содержит URL, регион и обязательных конкурентов. Кнопка изменения режима показывается только при наличии обязательных конкурентов.

При изменении региона набор ПС пересчитывается автоматически.

12. Создание задачи в Вебтронике

После подтверждения интерфейс показывает передачу параметров, затем карточку принятой задачи с номером, доменом, регионом, ПС, временем запуска и стартовым статусом.

В рабочей версии backend отправляет настройки в API Вебтроники и сохраняет ID задачи вместе с Telegram user ID.

Рекомендуемый входной payload: site_url, region, вычисляемый search_engines; если указаны обязательные конкуренты — массив required_competitors и required_competitors_mode. При пропуске шага конкурентов режим не передавать.

13. Автоматическое обновление статуса

Рекомендуется редактировать одно статусное сообщение, чтобы не засорять чат.

Пример последовательности: подготовка данных → сбор поисковой выдачи → внутренние анализы → формирование КП → финальная проверка.

Процент разрешено показывать только при наличии реального прогресса от API. Переключатель выше демонстрирует оба варианта.

14. Итоговый результат: только ссылки

После готовности бот не выводит пакет документов отдельными inline-кнопками. Результат приходит обычным сообщением со ссылками:

КП: ссылка
Анализ конкурентов: ссылка
Анализ КФ: ссылка
Технический SEO-аудит: ссылка
Ошибки на сайте: ссылка

В рабочей версии каждая ссылка должна вести на соответствующий документ или внутренний результат Вебтроники с учётом прав доступа пользователя.

Если документ не сформирован, не нужно отдавать пустой URL. Backend должен вернуть явный статус, а бот — показать, что результат недоступен.

Под итоговым сообщением располагается одна inline-кнопка Создать новое КП. Она запускает новый сценарий с чистыми параметрами без необходимости возвращаться к стартовому сообщению.

15. Формат результата API

Рекомендуемый объект результата:

proposal_url
competitors_analysis_url
commercial_factors_analysis_url
technical_audit_url
site_errors_url

Дополнительно желательно возвращать статус каждого документа: ready, processing, failed или not_created.

16. Ошибка формирования КП

Предусмотрен отдельный сценарий ошибки, включаемый переключателем в DEV-панели.

После ошибки доступны повторный запуск, изменение параметров и переход к задаче Вебтроники. При повторе используются уже собранные параметры.

17. Техническая структура прототипа
  • Один автономный HTML-файл.
  • Внутри находятся разметка, стили, JavaScript, демонстрационный справочник регионов и DEV-инструкции.
  • Внешние библиотеки и сетевые запросы не используются.
  • Состояние хранится в объекте JavaScript до перезагрузки страницы.
  • Поддерживаются desktop, tablet и mobile.
18. Будущая интеграция

Рекомендуемый поток:

Telegram → backend бота → API Вебтроники → ID задачи → webhook или polling → пакет URL → Telegram

  1. получать Telegram user ID;
  2. получать/синхронизировать актуальный список регионов Keyso;
  3. определять ПС по региону также на backend;
  4. создавать задачу через API Вебтроники;
  5. сохранять связь пользователь ↔ задача ↔ проект;
  6. получать статус через webhook либо polling;
  7. получать пять итоговых URL;
  8. обрабатывать частично готовый пакет документов;
  9. реализовать повторные попытки и защиту от дублирующего запуска;
  10. проверять права доступа к внутренним документам.
