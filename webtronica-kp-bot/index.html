1. Назначение прототипа

Прототип демонстрирует Telegram-сценарий запуска создания коммерческого предложения внутри Вебтроники.

  1. Бот по шагам собирает входные настройки.
  2. По выбранному региону автоматически определяет поисковую систему или обе поисковые системы.
  3. Передаёт задачу в Вебтронику.
  4. Показывает статус обработки.
  5. После готовности присылает КП и ссылки на внутренние документы, на основе которых оно было сформировано.

В HTML-версии все интеграции имитируются JavaScript без реальных API-запросов.

2. Общий дизайн и UX
  • Интерфейс имитирует Telegram Desktop и адаптируется под мобильный экран.
  • Сообщения бота расположены слева, пользователя — справа.
  • Используются inline-кнопки, время сообщений, состояние «печатает…» и автоматическая прокрутка.
  • DEV-панель постоянно видна на широком экране и открывается поверх чата на узком.
  • Все действия выполняются без перезагрузки страницы.
3. Актуальная последовательность диалога
  1. Команда «Создать КП».
  2. Ввод URL продвигаемого сайта.
  3. Выбор региона анализа.
  4. Автоматическое определение ПС по региону.
  5. Ввод обязательных доменов одним сообщением.
  6. Выбор режима обязательных доменов.
  7. Ввод исключаемых доменов.
  8. Итоговая проверка параметров.
  9. Запуск задачи внутри Вебтроники.
  10. Сообщение о принятии задачи.
  11. Автоматическое обновление статуса.
  12. Получение КП и внутренних документов Вебтроники.

Удалено из сценария: отдельный шаг выбора поисковой системы и отдельный шаг «Сводный отчёт по Яндексу и Google».

4. Команда «Создать КП»

Начальное сообщение содержит короткое объяснение и кнопку Создать КП. После клика бот запускает пошаговый сценарий и запрашивает URL сайта.

Кнопка полного сброса в шапке очищает состояние прототипа и возвращает пользователя к начальному экрану.

5. URL продвигаемого сайта

Поле обязательное. Допускаются адреса с протоколом, www и путём: example.ru, https://www.example.ru/catalog/.

  • Проверяется наличие корректного домена и доменной зоны.
  • Запрещаются пробелы и недопустимые символы.
  • Для дальнейшей логики значение нормализуется до домена без www.
  • При ошибке бот предлагает повторный ввод или отмену сценария.
6. Единый выбор региона

После URL бот сразу предлагает единый список регионов. Поисковая система пользователем больше не выбирается.

Быстрые кнопки прототипа:

  • Москва;
  • Санкт-Петербург;
  • Екатеринбург;
  • Н. Новгород;
  • Краснодар;
  • Киев;
  • Нью-Йорк;
  • Другой…

Кнопка «Другой…» используется для ручного ввода дополнительных регионов Яндекса.

7. Автоматическое определение поисковых систем

ПС — вычисляемое поле, а не пользовательская настройка.

  • Москва → Яндекс + Google.
  • Киев, Нью-Йорк → только Google.
  • Санкт-Петербург, Екатеринбург, Н. Новгород, Краснодар → только Яндекс.
  • Другой поддерживаемый регион из справочника Яндекса → только Яндекс.

После выбора региона бот показывает информационное подтверждение: какой регион выбран и в каких ПС будет выполняться анализ.

В backend рекомендуется хранить поле search_engines как массив, например ["yandex", "google"], ["google"] или ["yandex"].

8. Ручной ввод региона и проверка

После выбора «Другой…» пользователь вводит город вручную. Нормализация игнорирует регистр, пробелы, точки, дефисы и иные разделители. Например, ростов на дону преобразуется в Ростов-на-Дону.

Два разных сообщения об ошибке:

  • Если город не распознан: «Город указан неверно. Проверьте написание и попробуйте ещё раз».
  • Если город существует, но отсутствует в ограниченном справочнике Вебтроники: «Город отсутствует в списке доступных регионов. В таком случае рекомендуем указать Москва».

В рабочей версии справочник поддерживаемых регионов должен приходить из Вебтроники, а не храниться в коде бота.

9. Москва заменяет старую настройку сводного отчёта

Отдельная настройка «Сводный отчёт по Яндексу и Google» удалена.

Если выбран регион Москва, бот автоматически запускает сбор данных сразу по двум поисковым системам — Яндексу и Google. Это полностью заменяет старую логику включённого сводного отчёта.

Отдельное пользовательское поле combinedReport в новой реализации не требуется.

10. Обязательные домены

Пользователь отправляет один или несколько доменов одним сообщением, каждый домен — с новой строки. Шаг можно пропустить.

  • Каждая строка валидируется отдельно.
  • Допускаются URL с протоколом, www и путём.
  • Значения нормализуются до домена.
  • Удаляются дубликаты.
  • Запрещено добавлять продвигаемый домен.
  • Корректные строки сохраняются, даже если часть списка содержит ошибки.

Для ошибочных строк бот показывает причину и предлагает исправить только их либо продолжить.

11. Режим обязательных доменов

После ввода доменов пользователь выбирает один из трёх вариантов:

  1. Всегда добавлять в анализ — независимо от наличия в выдаче.
  2. Учитывать только при наличии в выдаче — включать только найденные в поиске домены.
  3. Анализировать только указанные домены — автоматический поиск конкурентов не выполняется.

Если обязательные домены не введены, бот предлагает сначала добавить их либо пропустить настройку режима.

12. Исключаемые домены

Пользователь может отправить несколько доменов одним сообщением, каждый с новой строки. Шаг можно пропустить.

  • Используется та же валидация URL/домена.
  • Исключаемый домен не может совпадать с продвигаемым сайтом.
  • Один домен не может одновременно находиться в обязательном и исключаемом списках.
13. Итоговая проверка и редактирование

Бот показывает карточку со всеми собранными параметрами и кнопками запуска, изменения и отмены.

В карточке поисковые системы отображаются информационно и вычисляются из региона. Пользователь не может редактировать их отдельно.

Раздел «Изменить параметры» содержит: URL, регион, обязательные домены, режим доменов и исключаемые домены.

При изменении региона набор ПС пересчитывается автоматически.

14. Создание задачи в Вебтронике

После подтверждения интерфейс показывает «Передаю параметры в Вебтронику…», затем карточку принятой задачи:

  • номер задачи;
  • домен;
  • регион;
  • автоматически определённые ПС;
  • время запуска;
  • начальный статус;
  • ссылку на задачу внутри Вебтроники.

В рабочей версии backend должен отправить настройки в API Вебтроники и сохранить полученный ID задачи вместе с Telegram user ID.

15. Автоматическое обновление статуса

Рекомендуется редактировать одно статусное сообщение, чтобы не засорять чат.

Пример последовательности: подготовка данных → сбор поисковой выдачи → формирование внутренних анализов → формирование КП → финальная проверка.

Процент разрешено показывать только при наличии реального прогресса от API. Переключатель выше демонстрирует оба варианта.

16. Готовое КП и пакет внутренних документов

После завершения бот отправляет карточку результата с доменом, регионом, вычисленными ПС и номером задачи.

Основной результат: кнопки «Открыть КП» и «Скачать PDF».

Дополнительно бот возвращает ссылки на внутренние документы Вебтроники, использованные при формировании КП:

  • Анализ конкурентов;
  • Анализ КФ;
  • Технический SEO-аудит;
  • Ошибки на сайте.

Эти кнопки должны открывать соответствующие внутренние результаты в Вебтронике, а не скачивать фиктивные локальные файлы.

Если отдельный документ не сформирован или завершился ошибкой, backend должен вернуть его статус. Кнопку нельзя вести на пустой URL: её нужно скрыть либо показать как недоступную с понятным статусом.

17. Формат результата API

Рекомендуется возвращать не одну ссылку, а объект результатов задачи. Пример смысловой структуры:

proposal_url
competitors_analysis_url
commercial_factors_analysis_url
technical_audit_url
site_errors_url

Дополнительно желательно возвращать статус каждого документа: ready, processing, failed или not_created.

18. Ошибка формирования КП

Предусмотрен отдельный сценарий ошибки. Его можно включить переключателем в начале DEV-панели.

Кнопки после ошибки: повторить запуск, изменить параметры или открыть задачу в Вебтронике. При повторе используются уже собранные параметры.

19. Техническая структура прототипа
  • Один автономный HTML-файл.
  • Внутри находятся разметка, стили, JavaScript, демонстрационные справочники и комментарии.
  • Внешние библиотеки и сетевые запросы не используются.
  • Состояние хранится в объекте JavaScript до перезагрузки страницы.
  • Поддерживаются desktop, tablet и mobile.
20. Будущая интеграция

Рекомендуемый поток:

Telegram → backend бота → API Вебтроники → ID задачи → webhook или polling → пакет результатов → Telegram

Необходимо реализовать:

  1. авторизацию и Telegram user ID;
  2. получение актуального справочника регионов;
  3. автоматическое определение ПС по региону на backend, а не только в интерфейсе;
  4. создание задачи через API;
  5. сохранение связи пользователь ↔ задача ↔ проект;
  6. webhook от Вебтроники либо периодическую проверку статуса;
  7. получение КП и ссылок на все внутренние документы;
  8. обработку частично готового пакета документов;
  9. повторные попытки и обработку ошибок;
  10. защиту от дублирующего запуска;
  11. проверку прав доступа к задаче и внутренним документам.
