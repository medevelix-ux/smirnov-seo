Инструкция для программиста · «Видимость и позиции»

Что нужно сделать и зачем

Нужно реализовать рабочий экран, который по нажатию «Обновить видимость» собирает свежие данные трех источников, рассчитывает показатели и показывает SEO-специалисту две разные картины. Общая картина всегда строится по полному доступному массиву Яндекс.Вебмастера и Google Search Console. Webtronica не задает количество запросов общего экрана: это отдельный контрольный список из нескольких десятков наиболее важных запросов с точными позициями. Один Webtronica-проект может содержать несколько срезов — например, Яндекс Москва, Google Москва и Яндекс Санкт-Петербург. Во вкладке Webtronica пользователь выбирает основной проект или проект ПФ, затем конкретный срез либо все срезы, и сравнивает точные позиции с фактическими показами поисковых панелей. Пользователь должен всегда видеть поисковую систему, регион, устройство, источник показателя и ограничения сопоставления.

Как экран должен работать простыми словами

1Пользователь запускает проверкуКнопка обновляет только блок видимости, не технический анализ, трафик или ссылки.
2Система собирает источникиЯндекс.Вебмастер и GSC формируют общий массив. Webtronica возвращает точные позиции по всем настроенным комбинациям ПС, региона и устройства.
3Система считает два набора показателейСначала агрегаты поисковых панелей, затем отдельные показатели для каждой пары «запрос + срез Webtronica» и общий итог без потери регионального контекста.
4ИИ объясняет результатИИ получает готовые факты, связывает их и пишет вывод. Он не считает позиции и не придумывает отсутствующие данные.

Что пользователь видит в общем режиме

  • Обзор общей видимости Яндекса и Google.
  • Количество запросов Яндекса считать по уникальным нормализованным запросам Яндекс.Вебмастера, количество запросов Google — отдельно по GSC.
  • Отдельные вкладки поисковых систем, зон роста и падений.
  • Динамику за период, которую вернули источники. Это не история сохраненных дашбордов.
  • Список запросов с доказательствами, источником и рассчитанным приоритетом строится по поисковым панелям и не ограничивается ядром Webtronica.
  • Яндекс и Google сопоставляются, но их ТОП-10 не складывается в один показатель.

Что пользователь видит во вкладке Webtronica

  • Переключатель «Основной проект / Проект ПФ». Проект ПФ показывать только при наличии связи в настройках.
  • Список срезов выбранного проекта: «Все настроенные срезы» и отдельные комбинации ПС, региона и устройства.
  • Переключатель источника: Webtronica, Я.Вебмастер, GSC или Сопоставление.
  • Состав запросов внутри этой вкладки всегда задает выбранный проект Webtronica. Источник меняет показатели, но не набор контрольного списка.
  • Покрытие показывает, сколько запросов контрольного списка реально найдено в каждой поисковой панели за период.
  • Для каждой строки показать точную позицию Webtronica и рядом среднюю позицию, показы, клики, CTR и фактический URL соответствующей поисковой панели.
  • Для основного проекта и ПФ отдельно считать агрегаты эффективности: среднюю точную позицию, среднюю позицию панели, показы, клики и CTR.
  • В режиме «Все срезы» количество ТОП-10 считать по парам «запрос + срез», а количество контрольных запросов — отдельно по уникальному тексту запроса.
  • Точный съем Webtronica и средняя позиция поисковой панели должны быть явно подписаны и не смешиваться.

Правила, которые нельзя нарушать

  • Основной проект и проект ПФ не объединять по умолчанию и не суммировать их запросы.
  • Количество запросов Webtronica нигде не использовать как количество запросов общего режима.
  • Не объединять запросы Яндекс.Вебмастера и GSC в одно искусственное число: объемы и доли рассчитывать отдельно по поисковым системам.
  • Если проект ПФ не настроен, не показывать пустую вкладку и не создавать искусственный проект.
  • Отсутствие запроса в Я.Вебмастере или GSC обозначать как «Не найден в источнике за период». Не трактовать это как отсутствие позиции.
  • Не использовать нечеткое или смысловое объединение запросов. Для присоединения данных нужен точный нормализованный текст.
  • Не усреднять точные позиции разных регионов в одну строку запроса. Сначала считать каждый срез отдельно; общий показатель строить только из уже подписанных пар.
  • Покрытие Яндекс.Вебмастера считать только среди Яндекс-пар, покрытие GSC — только среди Google-пар.
  • Рост запросов проекта ПФ не называть доказанным результатом поведенческих факторов. Допустима только формулировка о корреляции внутри выбранной группы.
  • Если поисковая панель не возвращает городскую детализацию, не приписывать ее CTR, показы и среднюю позицию выбранному городу. Показать ограничение и снизить уверенность вывода.

Источники данных

  • Яндекс.Вебмастер: запрос, URL, дата, показы, клики, CTR и средняя позиция.
  • Google Search Console: запрос, URL, дата, показы, клики, CTR и средняя позиция.
  • Webtronica: проекты, компактный контрольный список, query_id, запрос, поисковая система, регион, устройство, целевой URL, текущая и сравнительная точная позиция, дата съема.
  • Настройки SEO-проекта: основной Webtronica project_id, опциональный PF project_id, важные URL, регион, устройство, пороги сигналов.

Последовательность сбора

  • Один раз загрузить данные Я.Вебмастера и GSC за текущий и сравнительный периоды.
  • Нормализовать запросы и URL, затем отдельно рассчитать общие агрегаты и сигналы Яндекса и Google.
  • Получить конфигурацию связей и список доступных Webtronica-проектов.
  • Загрузить контрольные запросы и точные позиции основного проекта по всем настроенным ПС, регионам и устройствам; при наличии повторить для ПФ.
  • Для каждой строки Webtronica создать searchContextId и присоединить метрики панели той же ПС по нормализованному запросу.
  • Рассчитать показатели каждого среза, затем общий результат по подписанным парам и только после этого сформировать пакеты фактов для ИИ.

Как построить общий режим по поисковым панелям

function buildGeneralPanelView(panelRows, engine, periodType) { const sourceRows = panelRows.filter(row => row.engine === engine && row.periodType === periodType ); const queryGroups = groupBy(sourceRows, 'queryNormalized'); const queryAggregates = Object.values(queryGroups).map(aggregatePanelRows); return { queryCount: queryAggregates.length, impressions: sum(queryAggregates, 'impressions'), clicks: sum(queryAggregates, 'clicks'), ctr: ratio(sum(queryAggregates, 'clicks'), sum(queryAggregates, 'impressions')), positionBuckets: calculatePanelPositionDistribution(queryAggregates), queryAggregates }; } general.yandex = buildGeneralPanelView(rows, 'yandex', 'current'); general.google = buildGeneralPanelView(rows, 'google', 'current'); // Не делать union Яндекса и Google для единого queryCount. // Не ограничивать queryAggregates списком Webtronica.

Сначала объединить строки одного запроса по его URL внутри одной поисковой системы и периода. Затем считать количество запросов, позиционные диапазоны и сигналы. Текущий и сравнительный периоды агрегировать одинаково, после чего сопоставлять по ключу engine + queryNormalized.

Как присоединить Я.Вебмастер и GSC к контрольному списку Webtronica

function joinPanelMetrics(webtronicaRows, panelRows) { const panelIndex = groupBy(panelRows, row => `${row.engine}:${row.queryNormalized}` ); return webtronicaRows.map(wtRow => { const panelMetrics = aggregatePanelRows( panelIndex[`${wtRow.engine}:${wtRow.queryNormalized}`] ?? [] ); return { ...wtRow, panelMetrics, contextCompatibility: classifyContextCompatibility(wtRow, panelMetrics) }; }); } function classifyContextCompatibility(wtRow, panelMetrics) { if (!panelMetrics) return 'incompatible'; if ( panelMetrics.geographyScope === 'region' && panelMetrics.geographyIds.includes(wtRow.regionId) ) return 'exact'; return 'engine_only'; } function aggregatePanelRows(rows) { if (!rows.length) return null; const impressions = sum(rows, 'impressions'); const clicks = sum(rows, 'clicks'); return { impressions, clicks, ctr: impressions ? clicks / impressions : 0, averagePosition: weightedAverage(rows, 'averagePosition', 'impressions'), primaryUrl: maxBy(rows, 'impressions').url, urls: rows.map(row => row.url), geographyScope: mostSpecificCommonGeography(rows), geographyIds: unique(rows.map(row => row.geographyId).filter(Boolean)) }; }

Первый уровень — запрос по всем URL. Второй уровень — запрос + URL для диагностики расхождения посадочной и каннибализации. Основным фактическим URL считать URL с максимальным количеством показов за период. Присоединение выполняется по той же поисковой системе, но регион Webtronica не считать подтвержденным регионом панели, пока источник явно не вернул совместимую географию.

Состояния и ошибки

  • collecting: показать этапы Webtronica, Я.Вебмастер и GSC отдельно.
  • processing: нормализация, объединение и расчет сигналов.
  • interpreting: формирование и валидация ИИ-вывода.
  • partial: показать доступные источники; недоступный пометить и исключить из выводов.
  • failed: не удалять последний успешный результат, но пометить его как устаревший.
  • При 0 строк из панели показывать «Нет найденных запросов за период», а не ошибку интеграции.

Критерии приемки MVP

  • Отдельный запуск обновляет только блок видимости.
  • Яндекс и Google нигде не суммируются в общий ТОП.
  • Основной проект и ПФ переключаются независимо.
  • ПФ скрывается, если проект не подключен.
  • Список срезов строится из конфигурации выбранного Webtronica-проекта, а не захардкожен в интерфейсе.
  • Яндекс Москва и Google Москва отображаются и анализируются как разные searchContextId.
  • Общий режим использует полный доступный массив поисковых панелей и не фильтруется Webtronica.
  • Только внутри вкладки Webtronica данные панелей фильтруются составом выбранного проекта.
  • Количество запросов Яндекса и Google показано раздельно; количество Webtronica-запросов не подмешивается.
  • Покрытие Я.Вебмастера считается только от Яндекс-пар, GSC — только от Google-пар.
  • Точная и средняя позиция имеют разные подписи.
  • Для каждой точной позиции видны ПС, регион и устройство.
  • Несовпадение географии панели снижает уверенность и отображается как ограничение.
  • Во вкладке Webtronica для основного проекта и ПФ видны средняя позиция панели, показы, клики, CTR и фактический URL.
  • Отсутствующие строки не превращаются в нулевую позицию.
  • Смена целевого URL видна в таблице и детализации.
  • Каждый ИИ-тезис имеет доказательство.
  • ИИ получает системный и соответствующий режиму пользовательский промт; ответ проходит JSON-схему и evidence-валидацию.
  • Частичный результат не блокирует весь экран.
  • Мобильная таблица прокручивается и не ломает сетку.
Для расширенной версии: сохраняем место под историю запусков, сравнение произвольных снимков, долговременные статусы «новый / сохраняется / восстановлен» и причинный анализ проекта ПФ относительно контрольной группы. Что нужно сделать и зачем

Экран должен находить запросы и страницы, которые уже получают показы, но дают меньше кликов, чем сопоставимые запросы проекта на похожих позициях. Поисковые панели являются источником показов, кликов, CTR, средней позиции и фактического URL. Обход сайта дает title, description и H1. По отдельной кнопке специалист может точечно получить фактические сниппеты из той поисковой системы, откуда пришла строка запроса, и сравнить выдачу с HTML-метаданными. Все метрики и выбор запросов рассчитываются кодом; ИИ только интерпретирует готовые факты.

Как экран работает простыми словами

1Собираем поисковые строкиТекущий и равный сравнительный периоды из Я.Вебмастера и GSC.
2Присоединяем страницыПо нормализованному URL добавляем title, description, H1 и индексируемость из обхода.
3Считаем ориентирДля каждой группы позиций рассчитываем внутренний ожидаемый CTR и подтвержденные отклонения.
4При необходимости парсим выдачуПользователь выбирает сегмент, а сервис получает фактические сниппеты в исходной ПС каждой строки.
5ИИ объясняетМодель получает готовые факты и evidenceId, не пересчитывает CTR и не подменяет отсутствующий сниппет.

Источники

  • Яндекс.Вебмастер: query, URL, date, impressions, clicks, CTR, averagePosition.
  • GSC: query, page, date, impressions, clicks, CTR, averagePosition, device при доступности.
  • Обход сайта: final_url, status_code, content_type, robots_meta, x_robots_tag, canonical, title, description, H1.
  • SERP parser service: органические результаты Яндекса и Google по переданным query, engine, region, device; сервис должен возвращать контекст и технический статус попытки.
  • Настройки: брендовые маркеры, важные URL, регион/устройство парсинга, минимальные показы, пороги CTR-разрыва и длины метаданных.
  • Webtronica: необязательная отметка, входит ли запрос в контрольный проект. Общий массив CTR ей не ограничивается.

Границы анализа

  • До отдельного успешного парсинга метаданные страницы не являются фактически показанным сниппетом.
  • Полученный сниппет — контекстный снимок конкретных ПС, запроса, региона, устройства и времени, а не универсальный вид выдачи.
  • Title и description могут быть переписаны поисковой системой.
  • Ошибка парсера, CAPTCHA, rate limit или отсутствие совпавшего URL не означает отсутствия страницы в выдаче.
  • Низкий CTR вне ТОП-20 сам по себе не считать проблемой метаданных.
  • Яндекс и Google получают отдельные ориентиры CTR.
  • Длина title и description — индикатор проверки, а не гарантированная ошибка.
  • В MVP используется последний успешный снимок сниппета, без собственной истории запусков.

Что должна делать кнопка «Спарсить сниппеты»

Кнопка не запускает повторный сбор CTR. Она берет уже рассчитанные строки текущего анализа и предлагает шесть точных выборок: все запросы, CTR ниже ориентира, высокий потенциал кликов, умеренный CTR-разрыв, CTR ниже группы и коммерческий запрос. Агрегация поисковых строк

Единица CTR-анализа — один нормализованный запрос внутри поисковой системы и устройства. Если панель вернула для него несколько URL, показы и клики суммируются, а в строку выводится URL с наибольшим количеством показов. Иначе один запрос несколько раз попадет в когорту и исказит ориентир.

Как рассчитывается ориентир CTR

Ориентир — не внешний норматив и не число, придуманное ИИ. Это взвешенная медиана CTR сопоставимых запросов этого же проекта. Сначала ищем максимально точную группу: та же поисковая система, устройство, брендовый тип и диапазон позиции. Если данных мало, последовательно расширяем группу и обязательно сохраняем, какой уровень использован. Анализируемую строку из собственной контрольной группы исключаем.

const CTR_SIGNAL_THRESHOLDS = { minRowImpressions: 30, minQueries: 20, minCohortImpressions: 1000, maxCtrOpportunityPosition: 20, minDeficitRatio: 0.15, severeDeficitRatio: 0.35, minPotentialClicks: 1, highPotentialClicks: 5, noClicksImpressions: 100, positionComparableTolerance: 1.5, minCtrDropPp: 1, minComparablePeriodImpressions: 30, urlDominanceShare: 0.50 }; const BASELINE_LEVELS = [ { code: 'exact', fields: ['engine', 'device', 'brandType', 'positionBucket'] }, { code: 'without_brand', fields: ['engine', 'device', 'positionBucket'] }, { code: 'without_device', fields: ['engine', 'positionBucket'] } ]; function weightedQuantile(rows, valueField, weightField, quantile) { const sorted = [...rows].sort((a, b) => a[valueField] - b[valueField]); const totalWeight = sum(sorted, weightField); const targetWeight = totalWeight * quantile; let cumulativeWeight = 0; for (const row of sorted) { cumulativeWeight += row[weightField]; if (cumulativeWeight >= targetWeight) return row[valueField]; } return sorted.at(-1)?.[valueField] ?? null; } function calculateCtrBaseline(allRows, targetRow, settings) { for (const level of BASELINE_LEVELS) { const cohort = allRows.filter(row => row.id !== targetRow.id && row.impressions >= settings.minRowImpressions && row.averagePosition !== null && level.fields.every(field => row[field] === targetRow[field]) ); const reliable = countDistinct(cohort, 'queryNormalized') >= settings.minQueries && sum(cohort, 'impressions') >= settings.minCohortImpressions; if (reliable) return { expectedCtr: weightedQuantile(cohort, 'ctr', 'impressions', 0.50), cohortQ25Ctr: weightedQuantile(cohort, 'ctr', 'impressions', 0.25), baselineLevel: level.code, baselineReliable: true, cohortQueries: countDistinct(cohort, 'queryNormalized'), cohortImpressions: sum(cohort, 'impressions') }; } const fallback = settings.projectCtrFallback?.[targetRow.engine]?.[targetRow.positionBucket]; return fallback !== undefined ? { expectedCtr: fallback, cohortQ25Ctr: null, baselineLevel: 'project_fallback', baselineReliable: false, cohortQueries: 0, cohortImpressions: 0 } : { expectedCtr: null, cohortQ25Ctr: null, baselineLevel: 'unavailable', baselineReliable: false, cohortQueries: 0, cohortImpressions: 0 }; } // В расчетах CTR всегда decimal 0..1. Проценты нужны только для UI. function calculateCtrOpportunity(row, baseline) { const expectedCtr = baseline.expectedCtr; return { ctrGapPp: expectedCtr === null ? null : (row.ctr - expectedCtr) * 100, ctrDeficitRatio: expectedCtr > 0 ? max(0, (expectedCtr - row.ctr) / expectedCtr) : null, potentialClicks: expectedCtr === null ? 0 : max(0, round(row.impressions * expectedCtr) - row.clicks) }; }

Стартовые значения из CTR_SIGNAL_THRESHOLDS хранятся в настройках проекта и могут быть изменены администратором. expectedCtr отвечает на вопрос «какой CTR типичен», а cohortQ25Ctr — «ниже ли строка нижней четверти своей надежной группы». Потенциал кликов — расчетная величина при текущем числе показов, не прогноз будущего трафика.

Что означают сигналы простыми словами

Сигнал появляется только после числовой проверки. «CTR ниже ориентира» означает, что строка отстает от медианы сопоставимой группы минимум на установленную долю. «CTR ниже группы» — более строгий групповой факт: CTR оказался ниже нижнего квартиля надежной выборки. «Высокий потенциал кликов» означает, что при достижении внутреннего ориентира строка могла бы получить не менее заданного количества дополнительных кликов при том же объеме показов. «Умеренный CTR-разрыв» — заметное, но не критическое отставание. «Коммерческий запрос» не является ошибкой: это отдельный тег намерения пользователя, по которому можно отфильтровать строки для парсинга.

Точная логика присвоения CTR-сигналов

function calculateCtrSignalCodes(row, t) { const signals = []; // Для малого спроса CTR-сигналы не подтверждаем. if (row.impressions < t.minRowImpressions || row.averagePosition === null) { return { signalCodes: ['insufficient_data'], confidence: 'insufficient' }; } // За пределами ТОП-20 сначала работаем с позицией, а не со сниппетом. if (row.averagePosition > t.maxCtrOpportunityPosition) { return { signalCodes: ['position_priority_first'], confidence: 'medium' }; } if (row.clicks === 0 && row.impressions >= t.noClicksImpressions) { signals.push('high_impressions_no_clicks'); } const baselineAvailable = row.expectedCtr !== null && row.expectedCtr > 0; const belowExpected = baselineAvailable && row.ctrDeficitRatio >= t.minDeficitRatio && row.potentialClicks >= t.minPotentialClicks; if (belowExpected) signals.push('ctr_below_expected'); if (belowExpected && row.ctrDeficitRatio >= t.severeDeficitRatio) { signals.push('severe_ctr_gap'); } if (belowExpected && row.ctrDeficitRatio >= t.minDeficitRatio && row.ctrDeficitRatio < t.severeDeficitRatio) { signals.push('moderate_ctr_gap'); } // «Ниже группы» разрешен только при надежной выборке и известном Q25. if (belowExpected && row.baselineReliable && row.cohortQ25Ctr !== null && row.ctr < row.cohortQ25Ctr) { signals.push('ctr_below_group'); } if (belowExpected && row.potentialClicks >= t.highPotentialClicks) { signals.push('high_click_potential'); } return { signalCodes: unique(signals), confidence: calculateCtrSignalConfidence(row) }; } function detectPeriodSignals(current, previous, t) { const signals = []; const comparable = previous && current.impressions >= t.minComparablePeriodImpressions && previous.impressions >= t.minComparablePeriodImpressions && current.averagePosition !== null && previous.averagePosition !== null; if (comparable && abs(current.averagePosition - previous.averagePosition) <= t.positionComparableTolerance && current.ctrDeltaPp !== null && current.ctrDeltaPp <= -t.minCtrDropPp) { signals.push('ctr_drop'); } if (comparable && current.primaryUrl !== previous.primaryUrl && current.primaryUrlShare >= t.urlDominanceShare && previous.primaryUrlShare >= t.urlDominanceShare) { signals.push('ranking_url_changed'); } return signals; }

ctr_below_expected — общий код для фильтра «CTR ниже ориентира». Он может одновременно сопровождаться более конкретным кодом severe_ctr_gap, moderate_ctr_gap, ctr_below_group или high_click_potential. Все сработавшие условия сохраняются в signalCodes; интерфейс выбирает из них один главный бейдж.

Надежность сигнала

function calculateCtrSignalConfidence(row) { if (row.impressions < CTR_SIGNAL_THRESHOLDS.minRowImpressions) { return 'insufficient'; } if (row.averagePosition > CTR_SIGNAL_THRESHOLDS.maxCtrOpportunityPosition) { return 'medium'; } if (row.clicks === 0 && row.impressions >= CTR_SIGNAL_THRESHOLDS.noClicksImpressions) { return 'high'; } if (!row.baselineReliable) return row.expectedCtr !== null ? 'low' : 'insufficient'; const interval = wilsonInterval95(row.clicks, row.impressions); if (row.impressions >= 100 && interval.upper < row.expectedCtr) return 'high'; return 'medium'; }
  • Высокая: надежная проектная когорта, не менее 100 показов у строки, верхняя граница 95% Wilson-интервала ниже expected CTR; либо не менее 100 показов при нуле кликов.
  • Средняя: проектная когорта надежна, но статистическое подтверждение слабее; сюда же относится приоритет позиции за пределами ТОП-20.
  • Низкая: использован ориентир из настроек проекта, а не надежная текущая когорта.
  • Недостаточно данных: меньше 30 показов, нет позиции или нет ориентира. Красный/желтый CTR-бейдж не показывать.

Как рассчитывать приоритет строки

Сигнал отвечает на вопрос «что произошло», а priorityScore — «что смотреть раньше». Оценка строится детерминированно внутри каждой поисковой системы, чтобы больший объем Яндекса не подавлял Google. Для нормализации используем 95-й перцентиль текущего набора, а не захардкоженные абсолютные значения.

function calculateCtrPriority(row, engineStats, settings) { const demandScore = clamp01( log1p(row.impressions) / log1p(engineStats.p95Impressions || 1) ); const potentialScore = clamp01( row.potentialClicks / (engineStats.p95PotentialClicks || 1) ); const gapScore = clamp01( (row.ctrDeficitRatio || 0) / settings.severeDeficitRatio ); const businessScore = settings.importantUrls.includes(row.urlNormalized) ? 1 : row.intentTags.includes('commercial_query') ? 0.70 : 0.40; const confidenceFactor = { high: 1, medium: 0.80, low: 0.55, insufficient: 0.25 }[row.signalConfidence]; return round(100 * confidenceFactor * ( 0.30 * demandScore + 0.35 * potentialScore + 0.20 * gapScore + 0.15 * businessScore )); }

В evidence сохранить все четыре компонента, коэффициент уверенности и итоговый балл. Коммерческий интент повышает очередность, но сам по себе не создает проблемный сигнал. Для position_priority_first значение можно считать тем же способом, однако в UI причина приоритета должна быть подписана как работа с позицией.

Проверки метаданных

  • metadata_unavailable: URL не найден в обходе либо content_type не HTML.

Критерии приемки MVP

  • Экран запускается отдельно от видимости и остальных блоков.
  • Общий массив запросов берется из поисковых панелей.
  • Единица анализа — ПС + устройство + запрос; несколько URL одного запроса не создают дубли в CTR-когорте.
  • CTR в API и расчетах хранится как decimal 0..1, а в интерфейсе форматируется в проценты.
  • Яндекс и Google имеют отдельные baseline CTR и отдельную нормализацию priorityScore.
  • Ожидаемый CTR учитывает позицию, устройство и брендовый тип; анализируемая строка исключена из своей когорты.
  • Baseline является взвешенной медианой, а граница «ниже группы» — взвешенным Q25.
  • При малой выборке виден источник fallback-ориентира, количество запросов и показов когорты.
  • При fallback из настроек нельзя присвоить ctr_below_group, потому что Q25 неизвестен.
  • Строка с 29 показами получает insufficient_data, а с 30 показами проходит дальнейшие проверки.
  • Строка с позицией 20 может анализироваться по CTR, а с позицией выше 20 получает position_priority_first.
  • Порог дефицита 15% включительный: 15% — умеренный разрыв, 35% — сильный разрыв.
  • high_click_potential появляется только при одновременном CTR-разрыве и potentialClicks не ниже заданного порога.
  • Главный бейдж выбирается по PRIMARY_SIGNAL_ORDER; полный массив кодов не теряется.
  • При low confidence бейдж становится нейтральным и получает пометку «предварительно»; при insufficient не показывается как проблема.
  • commercial_query хранится как intent tag, не меняет severity и может лишь влиять на priorityScore.
  • Каждый сигнал содержит confidence и evidence с фактическими значениями и примененными порогами.
  • Потенциал кликов не называется прогнозом.
  • CTR сравнивается только с равным предыдущим периодом и при сопоставимых показах и позиции.
  • Метаданные присоединяются по нормализованному final URL.
  • Неиндексируемые и не-HTML URL помечаются отдельно.
  • Предпросмотр HTML не называется фактическим сниппетом.
  • Кнопка парсинга предлагает все шесть согласованных сегментов и показывает число строк.
  • CTR-сегменты парсинга формируются по signalCodes, коммерческий сегмент — по intentTags, всегда без участия ИИ.
  • Запрос Я.Вебмастера парсится в Яндексе, строка GSC — в Google.
  • В задании и карточке сохраняются query, engine, region, device и fetchedAt.
  • Парсер имеет отдельные состояния success, not_found, blocked, captcha, rate_limited и error.
  • Неуспешная попытка не затирает последний успешный сниппет.
  • Фактический сниппет и метаданные страницы отображаются рядом для сравнения.
  • Совпадение URL учитывает final URL, redirect map и canonical без скрытой склейки.
  • Все сигналы рассчитаны до ИИ.
  • Каждый тезис ИИ имеет evidenceId.
  • Поиск, фильтр ПС и четыре режима таблицы работают без перезапуска.
  • Запросы, URL, сниппеты и метаданные экранируются при выводе и не вставляются в DOM как доверенный HTML.

Что нужно сделать и зачем

Экран должен собрать по каждому нормализованному final URL единую диагностическую строку: есть ли поисковый спрос, сколько получено кликов и органических входов, привели ли эти входы к выбранным целям и доступна ли страница поисковому роботу. Сначала приложение объединяет источники и рассчитывает сигналы обычным кодом. ИИ получает только готовые факты и объясняет, где находится главный резерв проекта.

Как экран работает простыми словами

1Собираем URLБерем страницы из поисковых панелей, органические стартовые URL Метрики и final URL обхода.
2Приводим к одному видуУчитываем протокол, host, slash, параметры, редиректы и canonical по правилам проекта.
3Считаем сигналыОтдельно определяем рост, падение, спрос без входов, трафик без целей и технические блокеры.
4ИИ расставляет фокусМодель объясняет рассчитанные сигналы и не выдает гипотезу за подтвержденную причину.

Источники

  • Яндекс.Вебмастер: query, URL, impressions, clicks, CTR, averagePosition за текущий и равный сравнительный периоды.
  • GSC: query, page, impressions, clicks, CTR, averagePosition, device за те же периоды.
  • Яндекс.Метрика: органические визиты с измерением стартовой страницы, поисковой системы и устройства; уникальные конверсионные визиты и достижения выбранных целей.
  • Обход: final_url, status_code, content_type, robots_meta, x_robots_tag, canonical, title, description, H1, crawl_depth.
  • Настройки: выбранные цели, важные URL, бизнес-веса, правила URL, минимальные объемы данных и пороги сигналов.
  • Keys.so: необязательное обогащение кластера и интента. Не заменяет фактические метрики поисковых панелей.
  • Webtronica: необязательные точные позиции контрольных запросов. Не определяет общий список посадочных.

Важные ограничения

  • Клик панели и визит Метрики — разные сущности; их нельзя вычитать как потерю трафика.
  • Яндекс и Google агрегируются отдельно, общий итог строится только суммированием показов и кликов, а не усреднением CTR.
  • Достижения целей могут пересекаться. Для CR использовать уникальные конверсионные визиты.
  • При previousVisits = 0 относительную дельту не считать.
  • Не объединять URL только по похожей строке: сначала применить детерминированные правила URL и карту редиректов.
  • Если источник отсутствует, сохранять partial state и снижать уверенность, а не подставлять ноль.

Как определять коммерческий и информационный тип

Техническое состояние в таблице

  • Индексируется: final URL найден, status 200, HTML, нет robots/noindex/x-robots запрета, canonical отсутствует либо совпадает.
  • Canonical требует проверки: canonical указывает на другой URL, который не подтвержден как тот же final URL.
  • Индексируемый фильтр: URL совпал с правилами параметров/фильтров проекта и при этом доступен для индексации.
  • Не индексируется: подтвержден robots, noindex или x-robots запрет.
  • HTTP-ошибка: final status 4xx/5xx.
  • Не найдено в обходе: поисковый или аналитический URL не удалось связать с crawl URL. Это состояние данных, не доказательство удаления страницы.
  • При нескольких состояниях приоритет: 4xx/5xx → запрет индексации → индексируемый фильтр → canonical conflict → индексируется.

  • URL найден в поисковых панелях: есть хотя бы одна строка текущего либо сравнительного периода после нормализации.
  • Стартовый URL найден в Метрике: существует строка органического startURL. Если выгрузка Метрики успешна, но строки нет, это наблюдаемый ноль визитов; если выгрузка неуспешна, значение равно null.
  • Final URL найден в обходе: URL связан с результатом обхода напрямую либо через подтвержденную redirect_chain.
  • Canonical совпадает: canonical пустой/self либо после нормализации равен pageId. Canonical на другой URL дает «Требует проверки».
  • complete: обязательные источники успешно собраны, а URL не конфликтуют. partial: источник не собран или raw URL не удалось связать. conflict: источники указывают на разные final URL или canonical противоречит объединению.
  • source_url_unmatched ставится только для реально существующей строки источника, которую не удалось связать. Он не ставится просто из-за нуля визитов.

function calculateLandingPriority(page, settings) { const demand = normalizeLog(page.current.impressions, settings.demandP95); const traffic = normalizeLog(page.current.organicVisits, settings.visitsP95); const defaultBusinessWeight = { commercial: 0.70, informational: 0.45, mixed: 0.55, unknown: 0.40 }[page.intent]; const business = settings.urlWeights[page.pageId] ?? defaultBusinessWeight; const severity = maxSignalSeverity(page.signalCodes, { critical: 1, high: 0.80, medium: 0.55, positive: 0.35, info: 0.20 }); const blocker = hasTechnicalBlocker(page) ? 1 : 0; const confidence = { complete: 1, partial: 0.70, conflict: 0.55 }[page.dataQuality]; const priorityScore = round(100 * confidence * ( 0.28 * demand + 0.20 * traffic + 0.22 * business + 0.20 * severity + 0.10 * blocker )); return { priorityScore, priorityComponents: { demand, traffic, business, severity, blocker, confidence } }; } // demandP95 и visitsP95 считаются по текущему набору отдельно. // Явный urlWeights всегда приоритетнее значения по типу страницы. // Каждый компонент сохраняется рядом с результатом.

Положительный рост также может иметь высокий приоритет, если страница важна бизнесу и обладает большим спросом. Поэтому цвет сигнала и приоритет не являются одним показателем: зеленый бейдж не обязан означать низкий балл.

Главный фокус и уверенность

Главный фокус строится после всех расчетов. В ИИ передаются агрегаты KPI, группы primarySignalCode, максимум 20 страниц с наибольшим priorityScore и их evidence. Модель выбирает одну основную закономерность, но не меняет порядок страниц и числа. Критерии приемки MVP

  • Экран запускается отдельно от других модулей.
  • Текущий и сравнительный периоды имеют одинаковую длину и используют часовой пояс проекта.
  • URL объединяются через единый нормализатор и подтвержденную карту редиректов.
  • Canonical-конфликт не приводит к скрытой склейке данных.
  • Интент каждого запроса и страницы рассчитан до ИИ и содержит source, confidence и evidence.
  • Ручной page intent override имеет приоритет над запросами, Keys.so и шаблоном URL.
  • Страница с classifiedCoverage ниже 40% не получает query-weighted тип.
  • Доля коммерческого либо информационного интента ровно 65% является определяющей.
  • Mixed и unknown не попадают в фильтры «Коммерческие» и «Информационные».
  • Яндекс и Google доступны отдельно в данных строки; их позиции никогда не усредняются между собой.
  • Суммарный CTR страницы считается из суммы кликов и показов, а не средним значением CTR строк.
  • CR использует уникальные конверсионные визиты.
  • При нуле SEO-визитов CR представлен как null/«—», а не 0%.
  • Отсутствующий источник представлен как null/partial, а не как ноль.
  • Клики панели и визиты Метрики не сравниваются как равные величины.
  • При 9 SEO-визитах сигнал traffic_without_converted_visits не ставится; при 10 визитах и нуле convertedVisits ставится.
  • При 9 визитах в предыдущем периоде процентный сигнал падения не ставится; при базе 10 и снижении ровно на 20% ставится.
  • Ухудшение позиции ровно на 2 считается position drop; сравнение выполняется внутри одной ПС.
  • Переход с позиции 20 на 20,1 считается выходом из зоны 11–20 только при достаточных показах обоих периодов.
  • «Падение входов и позиций» требует одновременных кодов traffic drop и position drop.
  • «Рост при позиции 11–20» требует роста входов, текущей позиции 11–20 и минимум одного converted visit.
  • Главный бейдж выбирается по PRIMARY_LANDING_SIGNAL_ORDER, полный массив сигналов сохраняется.
  • Технический статус получается из crawl-полей по установленному порядку приоритета.
  • Каждый KPI можно пересчитать из массива страниц по формулам инструкции.
  • Уровни покрытия являются последовательными пересечениями и их ширина считается от индексируемых HTML-страниц.
  • Границы матрицы сохраняются в evidence; страницы на границе относятся к high.
  • Четыре ключевых сигнала над таблицей выбираются по формальным правилам, а не ИИ.
  • Каждый сигнал и priorityScore воспроизводимы без ИИ и содержат примененные пороги.
  • Страница с priorityScore ровно 80 входит во вкладку «Приоритеты».
  • Каждый тезис ИИ содержит существующий evidenceId и не изменяет intent или signalCode.
  • Поиск, тип страницы и пять режимов таблицы работают без перезапуска.
  • Выбор строки обновляет путь страницы и качество объединения.
  • Источник данных экранируется при рендеринге и не вставляется как доверенный HTML.
  • Частичные данные не ломают весь экран.
Для расширенной версии: история состояния конкретной посадочной между запусками, журнал смены ranking URL, аннотации внедренных изменений, сравнение сохраненных снимков и оценка результата эксперимента. В MVP используем только последний успешный запуск и текущий/равный сравнительный периоды самих источников.
