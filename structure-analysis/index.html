Классификация URL по паттернам конкретного конкурента ?

Keyso используется как обучающая выборка: backend сначала получает массовую выгрузку URL+запросы по конкуренту, затем ИИ определяет типы 20–30 разных URL и формирует паттерны, после чего основной массив Keyso и sitemap классифицируется кодом.

Важно: позиция запроса Keyso используется только для выбора 1–3 репрезентативных запросов по приоритету ТОП-3 → ТОП-10 → ТОП-20. Она не влияет на ценность страницы и финальный статус.

Обработка и дедупликация

Модуль сравнивает не URL, а смысловые сущности, затем сохраняет сомнительные и исключенные элементы.

Гибридный отбор страниц до смысловой обработки ?

До извлечения сущностей весь массив проходит техническую классификацию. ИИ анализирует только репрезентативные выборки, а полный список обрабатывается кодом по паттернам конкретного конкурента.

1
Keyso: URL + запросы

Для URL выбираются 1–3 разных запроса из первого доступного диапазона: ТОП-3, затем ТОП-10, затем ТОП-20.

2
Выборка 20–30 URL

URL отбираются из разных технических масок, глубин и семейств, а не случайно и не только по лучшим позициям.

3
ИИ формирует паттерны

Определяет технический класс, структурный тип, обязательные условия, исключения и положительные/отрицательные примеры.

4
Backend валидирует

Проверяет regex, пересечения, точность на размеченной выборке и активирует только безопасные правила.

5
Массовая классификация

Код применяет активные паттерны ко всему списку Keyso и присваивает classified, conflicted или unmatched.

6
Второй круг

Запускается по крупному остатку или конфликтам. Остаток снова группируется по новым маскам.

7
Title fallback

Title парсится только для неизвестных и конфликтных структурных URL после двух основных кругов.

8
Sitemap и основной pipeline

Паттерны применяются к sitemap. Далее проходят категории, подкатегории, теги и отдельный пул фильтров.

Этап извлечения смысловых сущностей ?

После технической классификации URL появляется отдельный обязательный слой: raw URL → extracted_entity → normalized_entity. На этот этап проходят только structural_landing, service, brand, brand_category, informational при включенном инфоразделе и отдельный пул filter_candidates.

Каждый элемент сначала получает статус “Кандидат”, затем переводится в один из финальных статусов.

создать

Новая страница нужна для расширения структуры.

объединить

Дубль или синоним уже существующей сущности.

сделать дочерней

Элемент должен быть вложен в родительскую группу.

сделать тегом

Коммерческая посадочная на базе фильтра/подборки.

сделать фильтром

Нужен как пользовательский фильтр, но не как SEO-страница.

оставить фильтром

Фильтр полезен, но не участвует в структуре SEO-страниц.

не создавать сейчас

исключить

DEV-инструкции для программиста

Полное описание общей логики и деталей реализации модуля анализа структуры конкурентов. В боевом интерфейсе этот раздел скрывается.

1. Общая логика работы модуля

Модуль предназначен для сбора, очистки, нормализации и сравнения структуры сайтов конкурентов с продвигаемым сайтом. Главная цель — получить список новых структурных страниц, которые можно создать на продвигаемом сайте для расширения охвата семантики.

Модуль не должен слепо копировать структуру конкурентов. Он собирает структурные сигналы из нескольких источников, объединяет их, удаляет дубли, группирует по смыслу, сравнивает с текущей структурой продвигаемого сайта и формирует итоговое дерево категорий, подкатегорий, тегов, брендов, фильтров и информационных страниц.

Важно: модуль не оценивает качество оптимизации уже существующих страниц. Статуса “оптимизировать” в модуле быть не должно.

Основной результат: итоговая структура сайта в виде дерева, таблица итоговых сущностей, список страниц “создать”, список страниц “есть на сайте”, список элементов на ручную проверку, список исключенных элементов, гостевое согласование, финальная генерация URL/H1/Title/Description.

2. Ввод проекта

Пользователь задает: домен продвигаемого сайта, регион, тип сайта, список конкурентов, учитывать ли инфораздел и учитывать ли бренды.

  • Домен: используется для сравнения структуры конкурентов с текущей структурой сайта, определения страниц “есть на сайте” и формирования рекомендуемых URL.
  • Регион: сохраняется как параметр проекта и может использоваться в шаблонах мета-тегов, но отдельный модуль мультирегиональности в MVP не реализуется.
  • Тип сайта: интернет-магазин, сайт услуг, агрегатор или портал. Влияет на классификацию страниц.
  • Конкуренты: по умолчанию берутся из модуля анализа конкурентов. Если анализа нет — система должна создать и запустить его, а затем взять сайты, автоматически отобранные для анализа КФ.
  • Инфораздел: по умолчанию выключен.
  • Бренды: по умолчанию включены.

Мультирегиональность в MVP убрана: не должно быть переключателя, отдельного слоя региональных URL, типа сущности region и логики поддоменов/городов в URL/Title/H1.

3. Настройка “Учитывать инфораздел”

Если переключатель выключен, статьи, блог, новости, гайды, FAQ и справочные страницы не попадают в итоговую коммерческую структуру. Они сохраняются в исключенных элементах с причиной “Инфораздел отключен в настройках проекта”.

Если переключатель включен, инфо-страницы анализируются отдельно от коммерческих страниц и попадают в группу “Информационные страницы”.

Типовые директории инфораздела:

/blog/ /articles/ /article/ /stati/ /statyi/ /news/ /novosti/ /guide/ /guides/ /help/ /faq/ /wiki/ /academy/ /knowledge/ /knowledge-base/ /poleznoe/ /info/ /information/ /reviews/ /obzory/ /sovety/ /kak-vybrat/ /how-to/ /instrukcii/ /manuals/

Инфораздел нельзя смешивать с категориями, тегами, брендами, услугами и фильтрами при дедупликации и сравнении.

4. Источники данных

В MVP используются четыре входных канала: Keyso, sitemap.xml, мега-меню и ручной импорт CSV/XLSX. Цель — собрать достаточно полную структуру без полного парсинга сайтов.

  • Keyso: массовая выгрузка URL + запрос + позиция по конкуренту; 1–3 репрезентативных запроса выбираются backend-кодом после группировки строк по URL. Источник обучает паттерны конкретного сайта.
  • Sitemap: опубликованные URL сайта. Нужен для полноты, но требует фильтрации.
  • Мега-меню: ручной добор навигационной структуры через DOM и/или скриншоты.
  • Manual import: структура, загруженная SEO-специалистом в CSV/XLSX.
5. Источник №1 — Keyso

Назначение источника: Keyso используется как основной источник SEO-видимых страниц конкурентов. Для MVP модулю нужны URL конкурента, Запрос и техническое поле позиция. Данные нужно получать массовой выгрузкой по конкуренту: backend забирает всю доступную семантику конкурента через отчет URL+запросы, проходит пагинацию этого отчета и уже после этого программно группирует строки по URL. Позиция используется только внутри backend для выбора 1–3 репрезентативных запросов по приоритету ТОП-3 → ТОП-10 → ТОП-20. Она не используется как показатель ценности страницы или фактор финального решения.

Авторизация: все запросы к API Keys.so должны выполняться с заголовком X-Keyso-TOKEN. Токен не хранить во фронтенде прототипа и не передавать в браузер. В рабочей реализации запросы к Keyso должны идти только через backend.

5.1. Основной метод MVP — массовая выгрузка URL и запросов по конкуренту

Для задачи анализа структуры основной метод — отчет «Органическая выдача — Запросы сайта», потому что он сразу возвращает связку word + url и позицию pos. Это должен быть один массовый сбор по домену конкурента с проходом пагинации, а не отдельные обращения по каждому URL. URL показывает посадочную конкурента, запрос помогает определить назначение страницы, а позиция используется только для последующего программного выбора репрезентативных запросов.

GET https://api.keys.so/report/simple/organic/sitepages/withkeys
Headers:
  X-Keyso-TOKEN: {KEYSO_TOKEN}

Query params:
  base={base}
  domain={competitor_domain}
  sort=url|asc
  page={page}
  per_page={per_page}

Принцип загрузки: backend вызывает этот отчет для домена конкурента и проходит страницы пагинации до last_page или внутреннего лимита проекта. Даже если API требует несколько HTTP-запросов из-за пагинации, логически это одна массовая выгрузка семантики конкурента, а не цикл запросов по URL.

Пример запроса:

GET https://api.keys.so/report/simple/organic/sitepages/withkeys?base=msk&domain=magmastones.ru&sort=url%7Casc&page=1&per_page=25

Какие поля использовать в MVP:

  • url — URL страницы конкурента;
  • word — поисковый запрос, связанный с URL;
  • pos — позиция запроса; используется только для отбора диапазона ТОП-3 / ТОП-10 / ТОП-20;
  • current_page, last_page, per_page, total — для пагинации.

Какие поля не использовать как SEO-метрики: ws, wsk, it1, it3, it5, it10, it50, vis, superwsk. Поле pos является исключением: оно используется только технически для отбора 1–3 запросов и не выводится как показатель ценности страницы.

Пример обработки строки ответа:

{
  "word": "мраморные слэбы купить",
  "pos": 3,
  "url": "/catalog/mramor/slaby/"
}

Результат для модуля:
{
  "competitor": "example.ru",
  "source": "keyso",
  "raw_url": "/catalog/mramor/slaby/",
  "query": "мраморные слэбы купить",
  "position": 3,
  "extracted_entity": "Мраморные слэбы",
  "page_type": "теговая страница",
  "group_type": "материал + изделие"
}

5.2. Дополнительный метод MVP — органические страницы сайта без запросов

Метод «Органическая выдача — страницы» можно использовать только как резервный способ получить список URL конкурента, если основной массовый отчет /sitepages/withkeys недоступен или вернул слишком мало данных. В этом режиме система получает URL, но не должна автоматически запускать отдельный запрос Keyso по каждому URL.

GET https://api.keys.so/report/simple/organic/sitepages
Headers:
  X-Keyso-TOKEN: {KEYSO_TOKEN}

Query params:
  base={base}
  domain={competitor_domain}
  sort=it50|desc
  page={page}
  per_page={per_page}

Пример запроса:

GET https://api.keys.so/report/simple/organic/sitepages?base=msk&domain=magmastones.ru&sort=it50%7Cdesc&page=1&per_page=25

Какие поля использовать в MVP:

  • url — URL страницы конкурента;
  • current_page, last_page, per_page, total — для пагинации.

Когда использовать: только как fallback для списка URL. Если запросов нет, URL получает признак no_keyso_queries = true и дальше уточняется через sitemap/menu/title fallback или ручную проверку. Массово подтягивать запросы через /keywords/bypage для каждого URL запрещено.

5.3. Метод по конкретной странице — только точечный fallback, не основной цикл

Метод «Органическая выдача — ключевые слова по странице» не должен использоваться для массовой обработки всех URL конкурента. Он допустим только как точечный fallback для единичных спорных URL после основной обработки, например при ручной проверке или при лимитированном доборе по самым важным unresolved-страницам. В MVP основной сценарий — вся семантика конкурента сначала выгружается массово через /sitepages/withkeys, а сортировка запросов по ТОП-3, ТОП-10 и ТОП-20 выполняется программно.

GET https://api.keys.so/report/simple/organic/keywords/bypage
Headers:
  X-Keyso-TOKEN: {KEYSO_TOKEN}

Query params:
  base={base}
  domain={competitor_domain}
  page_url={encoded_page_url}
  sort=pos|asc
  page={page}
  per_page={per_page}

Пример запроса:

GET https://api.keys.so/report/simple/organic/keywords/bypage?base=msk&domain=magmastones.ru&page_url=%2Fcatalog%2Fmramor%2Fslaby%2F&sort=pos%7Casc&page=1&per_page=25

Какие поля использовать в MVP:

  • word — запрос, по которому можно уточнить смысл страницы;
  • pos — позиция для выбора репрезентативного диапазона;
  • current_page, last_page, per_page, total — для пагинации.

5.4. Рекомендуемый алгоритм обращения к Keyso в MVP

  1. Для каждого конкурента взять домен и региональную базу base.
  2. Выполнить массовую выгрузку семантики конкурента через GET /report/simple/organic/sitepages/withkeys.
  3. Пройти все страницы пагинации этого отчета до last_page или до внутреннего лимита проекта. Это часть одной массовой выгрузки, а не обращение по каждому URL.
  4. После завершения выгрузки взять из каждой строки url, word и pos. Затем уже программно сгруппировать строки по URL и выбрать 1–3 неповторяющихся запроса из первого доступного диапазона: ТОП-3, иначе ТОП-10, иначе ТОП-20.
  5. Сохранить исходную строку в raw-лог. В рабочую карточку URL передать нормализованный URL, выбранные 1–3 запроса и диапазон отбора.
  6. Нормализовать URL: убрать протокол, www, UTM, сортировки, пагинацию, привести slash к единому виду.
  7. Сначала сформировать технические маски и репрезентативную выборку URL. Передавать данные на извлечение смысловой сущности только после классификации страниц и отбора структурных типов.
  8. Если /sitepages/withkeys не вернул пригодные данные, запросить GET /report/simple/organic/sitepages только для получения списка URL и пометить Keyso-источник как partial. Не запускать /keywords/bypage массово для каждого URL. Точечный /keywords/bypage разрешен только для ограниченного числа спорных URL как fallback после основной обработки.
  9. Если API вернул 202, повторить запрос позже по backoff-логике.
  10. Если API вернул 429, прочитать заголовок Retry-After и повторить запрос после указанной паузы.
  11. Если API вернул 401, зафиксировать ошибку авторизации и остановить сбор Keyso по проекту.
  12. Если API вернул 404, зафиксировать, что домен/ресурс не найден.

5.5. Пример backend-функции

async function fetchKeysoSitePagesWithKeys({
  token,
  domain,
  base = 'msk',
  page = 1,
  perPage = 100
}) {
  const url = new URL('https://api.keys.so/report/simple/organic/sitepages/withkeys');
  url.searchParams.set('base', base);
  url.searchParams.set('domain', domain);
  url.searchParams.set('sort', 'url|asc');
  url.searchParams.set('page', String(page));
  url.searchParams.set('per_page', String(perPage));

  const response = await fetch(url, {
    method: 'GET',
    headers: {
      'X-Keyso-TOKEN': token,
      'Accept': 'application/json'
    }
  });

  if (response.status === 202) {
    return { status: 'pending', retry: true };
  }

  if (response.status === 429) {
    return {
      status: 'rate_limited',
      retryAfter: response.headers.get('Retry-After')
    };
  }

  if (!response.ok) {
    const errorBody = await response.text();
    throw new Error(`Keyso API error ${response.status}: ${errorBody}`);
  }

  const data = await response.json();

  return {
    currentPage: data.current_page,
    lastPage: data.last_page,
    total: data.total,
    items: (data.data || []).map(row => ({
      source: 'keyso',
      domain,
      rawUrl: row.url,
      query: row.word,
      position: row.pos
    }))
  };
}

5.6. Пример функции получения всей массовой выгрузки с пагинацией

async function fetchAllKeysoUrlQueryPairs({ token, domain, base = 'msk' }) {
  const result = [];
  let page = 1;
  let lastPage = 1;

  do {
    const batch = await fetchKeysoSitePagesWithKeys({
      token,
      domain,
      base,
      page,
      perPage: 100
    });

    if (batch.status === 'pending') {
      await wait(10000);
      continue;
    }

    if (batch.status === 'rate_limited') {
      await wait(Number(batch.retryAfter || 60) * 1000);
      continue;
    }

    result.push(...batch.items);
    lastPage = batch.lastPage || page;
    page += 1;
  } while (page <= lastPage);

  return result;
}

{
  "project_id": 123,
  "competitor_id": 456,
  "source": "keyso",
  "raw_url": "/catalog/mramor/slaby/",
  "normalized_url": "example.ru/catalog/mramor/slaby/",
  "query": "мраморные слэбы купить",
  "position": 3,
  "raw_payload": "{...}",
  "created_at": "2026-07-20T12:00:00"

5.8. Что не делать в MVP

В MVP не использовать позиции как показатель ценности, приоритета или качества страницы. Поле pos разрешено использовать только технически — для выбора 1–3 репрезентативных запросов одного URL по диапазонам ТОП-3 → ТОП-10 → ТОП-20. Частотность, видимость, трафик, историю изменений и расширенные SEO-поля не использовать в логике MVP.

Важно: не обращаться к Keyso отдельно для каждого URL конкурента. Сначала выполняется массовая выгрузка семантики по конкуренту, затем backend сам группирует строки по URL, сортирует запросы по позициям и выбирает репрезентативные запросы. Метод /keywords/bypage не является основным механизмом сбора и не должен использоваться в цикле по всем URL.

6. Отбор URL, определение типов страниц и формирование URL-паттернов

Назначение: определить типы страниц каждого конкурента без построчной классификации всего массива через ИИ. ИИ анализирует ограниченную репрезентативную выборку и формирует правила конкретного сайта; backend валидирует правила и применяет их ко всему списку Keyso и sitemap.

Главная цепочка:

Массовая Keyso-выгрузка URL + запросы + позиции по конкуренту → программная группировка строк по URL → выбор 1–3 запросов по ТОП-3 / ТОП-10 / ТОП-20 → предварительные технические маски URL → репрезентативная выборка 20–30 URL → ИИ: технический класс + тип страницы + кандидаты паттернов → backend-валидация паттернов → массовая классификация Keyso кодом → второй круг по остатку при превышении порогов → Title fallback для неизвестных и конфликтных URL → применение паттернов к sitemap → дополнительный sitemap-круг по новым семействам → категории / подкатегории / теги в основной pipeline → фильтры в отдельный пул

6.1. Выбор запросов одного URL

На вход этого этапа поступает уже полученный массив строк из массовой выгрузки Keyso по конкуренту. На этом этапе запрещены дополнительные обращения к Keyso по каждому URL: вся сортировка, группировка и выбор запросов выполняются программно внутри backend.

  1. Сгруппировать строки Keyso по competitor_domain + normalized_url.
  2. Если есть запросы на позициях 1–3, использовать только этот диапазон.
  3. Если ТОП-3 пуст, использовать запросы из ТОП-10.
  4. Если ТОП-10 пуст, использовать запросы из ТОП-20.
  5. Если запросов в ТОП-20 нет, отметить URL как title_fallback_candidate = true.
  6. Выбирать максимум три запроса. Не добирать количество искусственно.
  7. Удалить полные дубли и почти одинаковые формулировки. Рекомендуемый порог похожести по леммам: Jaccard ≥ 0.80.
  8. Первым брать запрос с лучшей позицией, следующие — только если они добавляют новый смысловой признак.

Позиция используется только как технический критерий выбора запроса. Она не влияет на ценность страницы, статус “создать”, приоритет сущности или сравнение конкурентов.

6.2. Предварительные технические маски

До обращения к ИИ код группирует URL по техническим признакам: глубина, количество сегментов, статические директории, числа, SKU-подобные окончания, параметры, длина slug, наличие родителя и повторяющиеся части пути.

/catalog/granit/ /catalog/mramor/ → /catalog/{slug}/ /catalog/granit/dlya-fasada/ /catalog/mramor/dlya-fasada/ → /catalog/{slug}/{slug}/ /catalog/granit/black-galaxy-12345/ → /catalog/{category}/{product_slug}-{numeric_id}/

Предварительная маска нужна только для формирования разнообразной выборки и ещё не является типом страницы.

6.3. Репрезентативная выборка 20–30 URL

Выборка не должна быть случайной или состоять только из URL с лучшими позициями. Нужно покрыть разные технические семейства сайта.

  • 2–4 URL из самых массовых масок;
  • 1–2 URL из средних и редких масок;
  • URL разной глубины;
  • URL с числами, параметрами и нетипичными окончаниями;
  • URL без стандартной директории /catalog/, если они есть;
  • несколько URL, не попавших в устойчивую маску;
  • предпочтение URL с репрезентативными запросами.

Если пригодных URL меньше 20, использовать весь доступный список. Максимум одного batch — 30 URL.

6.4. Два уровня классификации

Технический класс: structural_landing, product, technical_filter, informational, service, utility, trash, unknown.

Структурный тип: category, subcategory, tag, filter, brand, brand_category, service, article, unknown.

Разделение обязательно: техническая маска /catalog/{category}/{slug}/ может одновременно содержать подкатегории, теги, фильтры и товары. Одна глубина URL не определяет смысловой тип.

6.5. Результат ИИ и режимы паттернов

ИИ должен вернуть классификацию примеров и формализованные паттерны с полями:

{ "pattern_id": "", "competitor_domain": "", "iteration": 1, "technical_class": "", "page_type": "", "path_template": "", "regex_candidate": "", "required_conditions": [], "excluded_conditions": [], "positive_examples": [], "negative_examples": [], "priority": 0, "confidence": 0, "pattern_mode": "deterministic | conditional | mixed | unsafe" }
  • deterministic: паттерн уверенно соответствует одному типу и может применяться кодом.
  • conditional: тип назначается только после проверки дополнительных условий.
  • mixed: маска содержит разные типы; автоматическая классификация запрещена.
  • unsafe: правило слишком широкое или слабо подтверждено.

6.6. Backend-валидация

Regex от ИИ является только кандидатом. До активации backend обязан:

  1. Проверить синтаксис и безопасность регулярного выражения.
  2. Проверить совпадение со всеми положительными примерами.
  3. Проверить отсутствие совпадения с отрицательными примерами.
  4. Применить правило ко всей размеченной выборке.
  5. Рассчитать точность и пересечения с другими типами.
  6. Не активировать правило, классифицирующее почти весь сайт одним типом.

Рекомендуемые пороги: confidence ≥ 0.75, precision_on_sample ≥ 0.80, покрытие собственных positive examples — 100%.

6.7. Приоритет правил

Правила применяются от наиболее специфичных к общим:

  1. служебные URL и мусор;
  2. информационные директории;
  3. параметрические фильтры;
  4. товары;
  5. бренды и бренд + категория;
  6. категории;
  7. подкатегории;
  8. теги;
  9. неизвестные структурные страницы.

При пересечении выбирается более высокий приоритет, затем более специфичное правило, затем большая уверенность. Неразрешённый конфликт получает processing_status = conflicted.

6.8. Первый круг массовой классификации Keyso

После активации паттернов код обрабатывает весь список URL текущего конкурента. Каждый URL получает:

{ "processing_status": "classified | conflicted | unmatched | excluded_by_hard_rule", "technical_class": "", "page_type": "", "matched_pattern_id": "", "pattern_version": 1, "classification_source": "hard_rule | site_pattern", "classification_confidence": 0 }

После круга посчитать покрытие паттернами, количество конфликтов, остаток и размеры неизвестных технических кластеров.

6.9. Второй круг

Второй круг запускается, если выполнено хотя бы одно условие:

  • unmatched_ratio > 15%;
  • unmatched_count > 100;
  • conflicted_ratio > 5%;
  • есть неизвестный кластер размером не менее 20 URL;
  • остались нераспознанные URL с запросами из ТОП-3 или ТОП-10.

Остаток повторно группируется по новым маскам. ИИ получает 20–30 представителей и краткий список уже активных паттернов. Результат сохраняется как новая версия набора. Максимум основных Keyso-итераций — две.

6.10. Title fallback

Title парсится только после двух основных попыток классификации и только для:

  • unmatched;
  • conflicted;
  • URL из mixed-паттернов;
  • URL без запросов в ТОП-20;
  • предположительно структурных страниц и крупных неизвестных кластеров.

Title не нужно получать для уже распознанных товаров, служебных URL, очевидных технических фильтров и всего сайта целиком.

6.11. Применение к sitemap

После завершения Keyso активный набор паттернов применяется к sitemap того же конкурента. Паттерны другого домена запрещены.

URL, не совпавшие с Keyso-паттернами, сохраняются в unmatched_sitemap, а не исключаются. Дополнительный sitemap-круг запускается при:

  • unmatched_sitemap_ratio > 15%;
  • unmatched_sitemap_count > 100;
  • новом кластере размером не менее 30 URL.

Для выборки новых sitemap-семейств разрешается получить Title и передать в ИИ URL + Title + sitemap_context. Максимум — один дополнительный sitemap-круг.

6.12. Разделение потоков после классификации

  • Основной пул: категории, подкатегории, теги.
  • Filter candidates: параметрические и ЧПУ-фильтры; далее решения “сделать тегом”, “сделать фильтром”, “оставить фильтром”, “исключить”.
  • Брендовый пул: только при brands_enabled = true.
  • Информационный пул: только при info_enabled = true; иначе сохранять в исключённых.
  • Исключённый пул: товары, служебные страницы, мусор, файлы и технические URL.

6.13. Хранение, версии и логирование

Для каждого URL сохранять выбранные запросы, диапазон позиций, preliminary mask, тип, источник классификации, matched_pattern_id, версию паттернов, уверенность, использование Title и причину ручной проверки.

Для каждого конкурента хранить отдельный versioned pattern set: домен, версию, prompt_version, дату, статистику покрытия, активные и отклонённые паттерны, positive/negative examples и историю изменений.

Кешировать результат по сочетанию: domain + normalized_url + representative_queries + title + pattern_set_version + prompt_version.

6.14. Критерии завершения

Этап завершён, когда все URL Keyso и sitemap получили технический статус; сохранён набор паттернов конкурента; конфликтные и неизвестные URL доступны отдельно; Title получен только для необходимого остатка; страницы разделены по потокам; категории, подкатегории и теги переданы на извлечение смысловой сущности и дедупликацию.

7. Источник №2 — sitemap.xml

Sitemap используется как источник опубликованной структуры сайта. Для каждого конкурента система должна сначала проверить robots.txt, затем стандартные варианты: /sitemap.xml, /sitemap_index.xml, /sitemap-index.xml, /sitemap1.xml, /sitemap-catalog.xml, /sitemap_categories.xml, /sitemap-tags.xml, /sitemap.xml.gz.

Если найден sitemap index, нужно обработать вложенные карты. Система должна различать sitemap категорий, товаров, тегов, брендов, статей, изображений и новостей.

Если sitemap содержит в основном товары, он не считается полноценным источником структуры и получает частичный балл. Товары не включаются в основную структуру, но могут использоваться как дополнительный сигнал для брендов.

8. Источник №3 — мега-меню

Мега-меню запускается вручную массово или по конкретному конкуренту, если Keyso/sitemap дали недостаточно данных. Основной способ — извлечение DOM-ссылок из header/nav/menu. Резервный способ — скриншоты раскрытых меню и ИИ-анализ изображения.

  1. Открыть сайт в эмулируемом браузере.
  2. Определить блоки навигации и каталога.
  3. Раскрыть меню через hover/click/focus.
  4. Извлечь DOM-ссылки.
  5. Сделать скриншоты раскрытых состояний, если DOM недостаточен.
  6. Передать скриншоты ИИ.
  7. Получить список пунктов, URL, родителей, уровней и типов сущностей.
  8. Сохранить source = mega_menu_dom или mega_menu_screenshot.
9. Источник №4 — ручной импорт CSV/XLSX

SEO-специалист может импортировать структуру в формате CSV или XLSX. Обязательные столбцы: URL и Страница.

После загрузки система читает файл, проверяет обязательные столбцы, нормализует URL, извлекает сущности из названий страниц, присваивает source = manual_import, добавляет строки в общий пул и запускает тот же pipeline: фильтрация → классификация → дедупликация → группировка → сравнение.

Импорт не должен перезаписывать существующую структуру. Если сущность совпала с уже найденной, manual_import добавляется как дополнительный источник подтверждения.

10. Нормализация URL и черный список

Все URL проходят техническую нормализацию: убрать http/https, www, якоря, UTM, сортировки, параметры пагинации, привести trailing slash и регистр домена к единому виду.

Черный список исключает технические URL: /cart/, /basket/, /compare/, /search/, /personal/, /order/, /checkout/, /delivery/, /payment/, /contacts/, /vacancy/, ?sort=, ?utm_, ?PAGEN_ и т.д.

Исключенные элементы не удаляются физически, а сохраняются в excluded_items с raw_url, normalized_url, source, competitor, detected_type, exclude_reason и created_at.

11. Разделение URL и смысловой сущности

Система должна хранить четыре уровня данных: сырой URL, извлеченная сущность, нормализованная страница и рекомендованная страница для продвигаемого сайта.

Пример: raw URL /catalog/granit/slaby/ → извлеченная сущность “Слэбы из гранита” → нормализованная страница “Гранитные слэбы” → рекомендованная страница с типом, родителем, URL и статусом.

Дедупликация выполняется по смыслу, а не по URL.

12. Классификация страниц

Каждый URL или элемент меню должен получить тип: главная категория, подкатегория, теговая страница, фильтр, брендовая страница, бренд+категория, услуга, статья, товар, служебная страница, мусор.

Для структуры особенно важны категории, подкатегории, коммерческие теги, бренды, бренд+категория, сценарии применения, характеристики и статьи, если включен инфораздел.

13. Нормализация и удаление дублей

Конкуренты могут называть одно и то же по-разному. Например: “Гранитные слэбы”, “Слэбы из гранита”, “Плиты из гранита”, “Гранит в слэбах”. Система должна привести такие элементы к одному каноническому названию.

Уровни дедупликации: техническая дедупликация URL, текстовая нормализация, семантическая дедупликация ИИ, ручная премодерация.

ИИ должен определять полный дубль, частичный дубль, родительскую/дочернюю сущность, разные сущности, фильтр без посадочной, мусор и ручную проверку.

14. Модель статусов

Все найденные элементы по умолчанию получают статус “Кандидат”. Финальные статусы: создать, есть на сайте, объединить, сделать дочерней страницей, сделать тегом, сделать фильтром, оставить фильтром, не создавать сейчас, исключить, ручная проверка, отклонено клиентом.

Есть на сайте означает только факт найденного аналога на продвигаемом сайте, а не качество оптимизации страницы.

Для элементов со статусом “ручная проверка” должен быть доступен select для изменения статуса. После изменения обновляются таблица, дерево, счетчики и история изменений.

15. Расчет полноты и уверенности ИИ

Полнота конкурента: (keyso_score + sitemap_score + menu_score) × coverage_factor. Keyso дает до 40 баллов, sitemap до 35, мега-меню до 25. Веса выбраны по силе источников: Keyso показывает SEO-видимые URL+запросы, sitemap показывает опубликованную структуру, меню дает навигационный добор.

Качество источника считается коэффициентом 0–1. Например: полноценный Keyso = 1.0, частичный = 0.3–0.6, нет данных = 0.

coverage_factor: 60+ элементов после фильтрации — 1.0; 30–59 — 0.85; 10–29 — 0.65; меньше 10 — 0.4.

Статусы полноты: 75–100 ОК, 50–74 средне, 20–49 недостаточно, 0–19 нет данных.

Уверенность ИИ: competitors_factor × 0.35 + source_factor × 0.25 + entity_clarity × 0.20 + hierarchy_clarity × 0.10 + conflict_score × 0.10.

16. Итоговая структура, фильтры и сравнение

Итоговая структура отображается таблицей и XMind-подобным деревом. Таблица содержит: страница, тип, уровень, группа, конкурентов, источники, уверенность, статус, рекомендуемый URL и действие.

Фильтр структуры должен поддерживать все канонические final_status: create, exists, merge, make_child, make_tag, make_filter, keep_filter, not_now, exclude, review. Фильтр применяется к таблице итоговых сущностей, таблице сравнения и дереву.

Вкладка “Сравнение” интегрирована в “Структуру”. Основная зона роста — “есть у конкурентов, но нет у нас”.

17. Гостевая ссылка и согласование клиентом

По гостевой ссылке клиент видит только дерево структуры и кнопку экспорта. Технические таблицы, промты и DEV скрыты.

Клиент может отклонять раздел, категорию, подкатегорию, тег или бренд. Отклоненный элемент получает client_status = rejected, визуально деактивируется, действие сохраняется с датой/временем, guest_token, user_agent/IP-хэшем и комментарием. Если отклонён родитель, дочерние элементы получают inherited_rejected или система запрашивает подтверждение каскада.

После клиентского согласования SEO-специалист получает утвержденный вариант и может отправить структуру на внедрение или запустить генерацию URL/мета.

18. Кнопка “Экспортировать”

Кнопка экспортирует итоговую таблицу структуры, чтобы было понятно, какая категория в каком разделе лежит, какие элементы являются тегами, фильтрами, брендами и т.д.

Минимальные колонки экспорта: ID, Parent ID, Level, раздел/родитель, страница, тип сущности, группа, рекомендуемый URL, H1, Title, Description, статус, источники, конкурентов, примеры URL конкурентов, уверенность ИИ, комментарий, статус клиента, комментарий клиента.

Приоритетный формат — XLSX; дополнительно можно поддержать CSV. По умолчанию экспортируются active-элементы: create, make_tag, make_child, exists, review, keep_filter. Exclude и rejected экспортируются только при отдельной настройке “включить исключенные/отклоненные”. Массивы sources, example_urls и example_queries сериализуются через перенос строки внутри ячейки.

19. Кнопка “Сгенерировать URL и мета-теги”

Кнопка запускает финальный этап после обработки и согласования структуры. Источник генерации — согласованное дерево из раздела “Структура” с учетом решений SEO-специалиста и клиента.

Генерировать нужно URL, H1, Title и Description для активных элементов со статусами: создать, сделать тегом, сделать дочерней страницей. Для статуса “есть на сайте” по умолчанию не генерировать, чтобы не перезаписывать существующие страницы.

Перед генерацией должно открываться модальное окно с шаблонами URL, H1, Title, Description, переключателем “перегенерировать для существующих” и спойлерами с редактируемыми промтами.

У каждого промта в модальном окне должны быть кнопки: редактировать, сохранить, сохранить и запустить генерацию, скопировать, сбросить.

20. Результат генерации URL и мета

После генерации система выводит таблицу: страница, тип, родитель, уровень, URL, H1, Title, Description, статус генерации, комментарий, действие.

Конфликтные строки должны получать статус manual_review. Примеры конфликтов: exact_duplicate, existing_url_conflict, too_similar, wrong_parent, invalid_slug, too_long.

21. Таблицы данных и ограничения MVP

Рекомендуемые сущности хранения: raw_urls, extracted_entities, normalized_entities, entity_sources, excluded_items, manual_decisions, guest_decisions.

Ограничения MVP: нет полного краулинга, нет оценки качества оптимизации существующих страниц, нет автоматического создания страниц на сайте, нет автоматической публикации мета-данных, нет расширенных Keyso-полей кроме URL+Запрос.

Главная цепочка: ввод проекта → получение конкурентов → сбор Keyso → выбор репрезентативных запросов → обучение URL-паттернов → массовая классификация Keyso → сбор sitemap → применение и уточнение паттернов → оценка полноты → мега-меню при необходимости → ручной импорт → извлечение сущностей → дедупликация → группировка → сравнение с сайтом → статусы → гостевое согласование → генерация URL и мета.
