Обработка и дедупликация

Модуль сравнивает не URL, а смысловые сущности, затем сохраняет сомнительные и исключенные элементы.

Финальные статусы ?

Каждый элемент сначала получает статус “Кандидат”, затем переводится в один из финальных статусов.

создать

Новая страница нужна для расширения структуры.

объединить

Дубль или синоним уже существующей сущности.

сделать дочерней

Элемент должен быть вложен в родительскую группу.

сделать тегом

Коммерческая посадочная на базе фильтра/подборки.

сделать фильтром

Нужен как пользовательский фильтр, но не как SEO-страница.

оставить фильтром

Фильтр полезен, но не участвует в структуре SEO-страниц.

не создавать сейчас

Недостаточно доказательств или ассортимента.

исключить

Мусор, служебная страница, товар или нерелевантный URL.

ручная проверка

DEV-инструкции для программиста

Полное описание общей логики и деталей реализации модуля анализа структуры конкурентов. В боевом интерфейсе этот раздел скрывается.

1. Общая логика работы модуля

Модуль предназначен для восстановления структуры сайта на основе конкурентных данных. Он не краулит сайты полностью, а собирает структурные сигналы из ограниченного набора источников, нормализует их и превращает в список страниц для создания, согласования и дальнейшей генерации URL/мета.

  1. Пользователь задает проект, регион, тип сайта, конкурентов и настройки учета инфораздела/брендов/регионов.
  2. Система собирает URL и элементы структуры из Keyso, sitemap.xml и мега-меню.
  3. Пользователь может дополнительно загрузить свою структуру в CSV/XLSX со столбцами URL и Страница.
  4. Все источники объединяются в единый пул raw items.
  5. Пул очищается по черному списку и правилам исключения товаров/техстраниц.
  6. Из каждого URL или пункта меню извлекается смысловая сущность.
  7. ИИ объединяет дубли, синонимы и разные URL-форматы в нормализованные страницы.
  8. Система сравнивает итоговые сущности с продвигаемым сайтом.
  9. Каждая сущность получает финальный статус.
  10. SEO-специалист и клиент согласуют дерево структуры.
  11. После согласования запускается генерация URL, Title, Description и H1.

Статус “оптимизировать” не используется, потому что модуль не оценивает качество существующих страниц. Он определяет, какие новые страницы стоит создать и какие уже есть на сайте.

3. Источники данных

В MVP используются только четыре входных канала: Keyso, sitemap.xml, мега-меню и ручной импорт структуры.

  • Keyso — источник SEO-видимых URL и запросов. Самый сильный сигнал, потому что показывает страницы, которые уже участвуют в поисковом спросе.
  • Sitemap — источник опубликованной структуры сайта. Нужен для полноты, но может содержать товары и технический мусор.
  • Мега-меню — источник навигационной структуры. Запускается вручную для конкурентов с низкой полнотой.
  • Ручной импорт — пользовательская структура в CSV/XLSX. Используется, если у SEO-специалиста уже есть выгрузка структуры или черновой список страниц.

Каждая итоговая сущность должна хранить evidence: список конкурентов, исходные URL, источник, уверенность и комментарии ИИ.

4. Ручной импорт CSV/XLSX

Импорт нужен для объединения внешней структуры с автоматически собранной. Файл должен иметь обязательные колонки URL и Страница.

  1. Пользователь выбирает CSV или XLSX.
  2. Система валидирует наличие колонок URL и Страница.
  3. Каждая строка превращается в raw_item с source_type = manual_import.
  4. Если URL пустой, но есть название страницы, сущность все равно создается как кандидат.
  5. После импорта строки проходят тот же pipeline: фильтрация → извлечение сущности → дедупликация → группировка → сравнение с сайтом.
  6. Если импортированная сущность совпала с уже найденной, она не дублируется, а добавляется как дополнительный источник подтверждения.

XLSX можно обрабатывать на backend или через библиотеку на клиенте. В прототипе показана только UI-логика.

5. Обработка Keyso

Из Keyso берутся URL конкурентов, запросы и при наличии частотность/видимость. URL нормализуются технически: http/https, www/non-www, слеши, UTM и параметры.

Keyso получает высокий вес, потому что показывает не просто существующие страницы, а SEO-активные страницы. Поэтому в расчете полноты источник Keyso может дать до 40 баллов.

6. Обработка sitemap.xml

Алгоритм поиска: сначала robots.txt, затем резервные адреса /sitemap.xml, /sitemap_index.xml, /sitemap-index.xml, /sitemap1.xml, /sitemap-catalog.xml, /sitemap_categories.xml, /sitemap-tags.xml, /sitemap.xml.gz. Если найден sitemap index, обрабатываются вложенные карты.

Товарные sitemap не используются как основа структуры, но могут помогать в определении брендов. Если sitemap содержит только товары, источник получает частичный балл.

7. Обработка мега-меню

Мега-меню запускается вручную массово или по отдельному конкуренту. Основной способ — извлечение DOM-ссылок из header/nav/menu. Fallback — скриншоты раскрытых меню и ИИ-анализ изображения.

Результат мега-меню не заменяет Keyso/sitemap, а добавляется в общий пул. Если элемент меню совпадает с уже найденной сущностью, он усиливает evidence.

8. Фильтрация и черный список

Перед классификацией URL проходят техническую фильтрацию. Исключаются товары, корзина, сравнение, поиск, пагинация, сортировки, UTM, служебные страницы, PDF, изображения и URL по черному списку.

Исключенные элементы нельзя удалять физически: они сохраняются в excluded_items с причиной, чтобы SEO-специалист мог проверить решения системы.

9. Классификация URL и сущностей

Каждый raw item получает page_type и entity_type. Для структуры важны: категория, подкатегория, тег, фильтр, бренд, бренд+категория, услуга, статья, региональная страница.

Для magmastones.ru используются типы: материал, изделие, применение, бренд/поставщик, инфораздел, фильтр.

10. Дедупликация и нормализация

Дедупликация выполняется по смыслу, а не по URL. ИИ объединяет синонимы, разные падежи, транслитерации, близкие URL и перестановки слов.

Пример: “слэбы гранита”, “гранитные слэбы”, “granit slabs” → одна нормализованная сущность “Гранитные слэбы”.

11. Сравнение с продвигаемым сайтом

Сравнение теперь является частью вкладки “Структура”. Система определяет, есть ли аналог нормализованной сущности на magmastones.ru.

Сравнение идет по нормализованной сущности и возможным URL/названиям, а не только по точному URL. Если аналог найден, сущность получает статус “Есть на сайте”.

12. Статусы и ручная смена статусов

Допустимые статусы: создать, есть на сайте, объединить, сделать дочерней, сделать тегом, сделать фильтром, оставить фильтром, не создавать сейчас, исключить, ручная проверка.

Для элементов со статусом “ручная проверка” в таблице сравнения должен быть доступен select для изменения статуса. После изменения статус должен сохраняться в normalized_entity.final_status и использоваться в дереве и генерации URL/мета.

13. Фильтр структуры по статусам

Во вкладке “Структура” должен быть фильтр отображения: создать, есть на сайте, ручная проверка. Фильтр применяется к таблице итоговых сущностей, встроенной таблице сравнения и дереву.

В MVP фильтр может скрывать элементы на клиенте. В боевой версии желательно фильтровать данные на уровне состояния приложения.

14. Генерация URL и мета

Кнопка “Сгенерировать URL и мета” запускает финальный этап после согласования структуры. Генерировать нужно только для сущностей со статусом “создать” или утвержденных вручную статусов, если SEO-специалист разрешил генерацию.

Результат: recommended_url, Title, Description, H1, parent_url, комментарий по внедрению. Для статуса “есть на сайте” мета не генерируются как новые, но могут использоваться как справка.

15. Гостевая ссылка и согласование клиентом

По гостевой ссылке клиент видит только дерево структуры и кнопку экспорта. Он может отклонять узлы. Отклонение сохраняется как client_status = rejected.

Если клиент отклонил родительскую ветку, дочерние элементы должны либо автоматически получать inherited_rejected, либо требовать отдельного подтверждения — это нужно определить в настройках проекта.

16. Экспорт структуры

Экспорт должен включать: страницу, тип, уровень, родителя, группу, источники, конкурентов, уверенность, финальный статус, клиентский статус, recommended_url, Title, Description, H1.

17. Ограничения MVP

В MVP нет полного краулинга сайта, нет оценки качества оптимизации существующих страниц, нет автоматического создания задач и нет реального backend-парсинга XLSX в прототипе. Но интерфейс и модель данных должны быть подготовлены под эти сценарии.
