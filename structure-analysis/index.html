Модуль сравнивает не URL, а смысловые сущности, затем сохраняет сомнительные и исключенные элементы.

Финальные статусы ?

Каждый элемент сначала получает статус “Кандидат”, затем переводится в один из финальных статусов.

создать

Новая страница нужна для расширения структуры.

объединить

Дубль или синоним уже существующей сущности.

сделать дочерней

Элемент должен быть вложен в родительскую группу.

сделать тегом

Коммерческая посадочная на базе фильтра/подборки.

сделать фильтром

Нужен как пользовательский фильтр, но не как SEO-страница.

оставить фильтром

Фильтр полезен, но не участвует в структуре SEO-страниц.

не создавать сейчас

исключить

DEV-инструкции для программиста

Полное описание общей логики и деталей реализации модуля анализа структуры конкурентов. В боевом интерфейсе этот раздел скрывается.

1. Общая логика работы модуля

Модуль предназначен для сбора, очистки, нормализации и сравнения структуры сайтов конкурентов с продвигаемым сайтом. Главная цель — получить список новых структурных страниц, которые можно создать на продвигаемом сайте для расширения охвата семантики.

Модуль не должен слепо копировать структуру конкурентов. Он собирает структурные сигналы из нескольких источников, объединяет их, удаляет дубли, группирует по смыслу, сравнивает с текущей структурой продвигаемого сайта и формирует итоговое дерево категорий, подкатегорий, тегов, брендов, фильтров и информационных страниц.

Важно: модуль не оценивает качество оптимизации уже существующих страниц. Статуса “оптимизировать” в модуле быть не должно.

Основной результат: итоговая структура сайта в виде дерева, таблица итоговых сущностей, список страниц “создать”, список страниц “есть на сайте”, список элементов на ручную проверку, список исключенных элементов, гостевое согласование, финальная генерация URL/H1/Title/Description.

2. Ввод проекта

Пользователь задает: домен продвигаемого сайта, регион, тип сайта, список конкурентов, учитывать ли инфораздел и учитывать ли бренды.

  • Домен: используется для сравнения структуры конкурентов с текущей структурой сайта, определения страниц “есть на сайте” и формирования рекомендуемых URL.
  • Регион: сохраняется как параметр проекта и может использоваться в шаблонах мета-тегов, но отдельный модуль мультирегиональности в MVP не реализуется.
  • Тип сайта: интернет-магазин, сайт услуг, агрегатор или портал. Влияет на классификацию страниц.
  • Конкуренты: по умолчанию берутся из модуля анализа конкурентов. Если анализа нет — система должна создать и запустить его, а затем взять сайты, автоматически отобранные для анализа КФ.
  • Инфораздел: по умолчанию выключен.
  • Бренды: по умолчанию включены.

Мультирегиональность в MVP убрана: не должно быть переключателя, отдельного слоя региональных URL, типа сущности region и логики поддоменов/городов в URL/Title/H1.

3. Настройка “Учитывать инфораздел”

Если переключатель выключен, статьи, блог, новости, гайды, FAQ и справочные страницы не попадают в итоговую коммерческую структуру. Они сохраняются в исключенных элементах с причиной “Инфораздел отключен в настройках проекта”.

Если переключатель включен, инфо-страницы анализируются отдельно от коммерческих страниц и попадают в группу “Информационные страницы”.

Типовые директории инфораздела:

Инфораздел нельзя смешивать с категориями, тегами, брендами, услугами и фильтрами при дедупликации и сравнении.

4. Источники данных

В MVP используются четыре входных канала: Keyso, sitemap.xml, мега-меню и ручной импорт CSV/XLSX. Цель — собрать достаточно полную структуру без полного парсинга сайтов.

  • Keyso: URL конкурента + запрос. Самый сильный SEO-сигнал.
  • Sitemap: опубликованные URL сайта. Нужен для полноты, но требует фильтрации.
  • Мега-меню: ручной добор навигационной структуры через DOM и/или скриншоты.
  • Manual import: структура, загруженная SEO-специалистом в CSV/XLSX.
5. Источник №1 — Keyso

Назначение источника: Keyso используется как основной источник SEO-видимых страниц конкурентов. Для MVP модулю нужны только два смысловых поля: URL конкурента и Запрос. Запрос нужен, чтобы точнее определить смысловую сущность страницы, когда сам URL неоднозначен.

Авторизация: все запросы к API Keys.so должны выполняться с заголовком X-Keyso-TOKEN. Токен не хранить во фронтенде прототипа и не передавать в браузер. В рабочей реализации запросы к Keyso должны идти только через backend.

5.1. Основной метод MVP — страницы сайта с запросами

Для задачи анализа структуры основной метод — отчет «Органическая выдача — Запросы сайта», потому что он сразу возвращает связку word + url. Это как раз то, что нужно модулю: запрос помогает понять смысл страницы, а URL показывает посадочную конкурента.

GET https://api.keys.so/report/simple/organic/sitepages/withkeys
Headers:
  X-Keyso-TOKEN: {KEYSO_TOKEN}

Query params:
  base={base}
  domain={competitor_domain}
  sort=url|asc
  page={page}
  per_page={per_page}

Пример запроса:

GET https://api.keys.so/report/simple/organic/sitepages/withkeys?base=msk&domain=magmastones.ru&sort=url%7Casc&page=1&per_page=25

Какие поля использовать в MVP:

  • url — URL страницы конкурента;
  • word — поисковый запрос, связанный с URL;
  • current_page, last_page, per_page, total — для пагинации.

Какие поля можно получить в ответе, но в MVP не использовать как метрики: ws, wsk, pos, it1, it3, it5, it10, it50, vis, superwsk. Их можно сохранить как raw-данные, но не использовать в логике MVP и не выводить в интерфейс как обязательные показатели.

Пример обработки строки ответа:

{
  "word": "мраморные слэбы купить",
  "url": "/catalog/mramor/slaby/"
}

Результат для модуля:
{
  "competitor": "example.ru",
  "source": "keyso",
  "raw_url": "/catalog/mramor/slaby/",
  "query": "мраморные слэбы купить",
  "extracted_entity": "Мраморные слэбы",
  "page_type": "теговая страница",
  "group_type": "материал + изделие"
}

5.2. Дополнительный метод MVP — органические страницы сайта

Метод «Органическая выдача — страницы» можно использовать как дополнительный способ получить список URL конкурента, если нужно сначала собрать страницы, а затем отдельно получить запросы по каждой странице.

GET https://api.keys.so/report/simple/organic/sitepages
Headers:
  X-Keyso-TOKEN: {KEYSO_TOKEN}

Query params:
  base={base}
  domain={competitor_domain}
  sort=it50|desc
  page={page}
  per_page={per_page}

Пример запроса:

GET https://api.keys.so/report/simple/organic/sitepages?base=msk&domain=magmastones.ru&sort=it50%7Cdesc&page=1&per_page=25

Какие поля использовать в MVP:

  • url — URL страницы конкурента;
  • current_page, last_page, per_page, total — для пагинации.

Когда использовать: если метод /sitepages/withkeys временно недоступен, возвращает мало данных или нужно быстро получить список страниц, а запросы подтянуть вторым шагом через метод /keywords/bypage.

5.3. Дополнительный метод MVP — запросы по конкретной странице

Метод «Органическая выдача — ключевые слова по странице» используется для уточнения смысловой сущности конкретного URL. Особенно полезен, если из URL неясно, какую страницу он представляет.

GET https://api.keys.so/report/simple/organic/keywords/bypage
Headers:
  X-Keyso-TOKEN: {KEYSO_TOKEN}

Query params:
  base={base}
  domain={competitor_domain}
  page_url={encoded_page_url}
  sort=pos|asc
  page={page}
  per_page={per_page}

Пример запроса:

GET https://api.keys.so/report/simple/organic/keywords/bypage?base=msk&domain=magmastones.ru&page_url=%2Fcatalog%2Fmramor%2Fslaby%2F&sort=pos%7Casc&page=1&per_page=25

Какие поля использовать в MVP:

  • word — запрос, по которому можно уточнить смысл страницы;
  • current_page, last_page, per_page, total — для пагинации.

5.4. Рекомендуемый алгоритм обращения к Keyso в MVP

  1. Для каждого конкурента взять домен и региональную базу base.
  2. Сначала запросить GET /report/simple/organic/sitepages/withkeys.
  3. Пройти все страницы пагинации до last_page или до внутреннего лимита проекта.
  4. Из каждой строки взять только url и word.
  5. Сохранить исходную строку в raw-лог, но в MVP использовать только URL и запрос.
  6. Нормализовать URL: убрать протокол, www, UTM, сортировки, пагинацию, привести slash к единому виду.
  7. Передать пару url + word в блок извлечения смысловой сущности.
  8. Если /sitepages/withkeys не вернул пригодные данные, запросить GET /report/simple/organic/sitepages и затем для важных URL получить запросы через GET /report/simple/organic/keywords/bypage.
  9. Если API вернул 202, повторить запрос позже по backoff-логике.
  10. Если API вернул 429, прочитать заголовок Retry-After и повторить запрос после указанной паузы.
  11. Если API вернул 401, зафиксировать ошибку авторизации и остановить сбор Keyso по проекту.
  12. Если API вернул 404, зафиксировать, что домен/ресурс не найден.

5.5. Пример backend-функции

async function fetchKeysoSitePagesWithKeys({
  token,
  domain,
  base = 'msk',
  page = 1,
  perPage = 100
}) {
  const url = new URL('https://api.keys.so/report/simple/organic/sitepages/withkeys');
  url.searchParams.set('base', base);
  url.searchParams.set('domain', domain);
  url.searchParams.set('sort', 'url|asc');
  url.searchParams.set('page', String(page));
  url.searchParams.set('per_page', String(perPage));

  const response = await fetch(url, {
    method: 'GET',
    headers: {
      'X-Keyso-TOKEN': token,
      'Accept': 'application/json'
    }
  });

  if (response.status === 202) {
    return { status: 'pending', retry: true };
  }

  if (response.status === 429) {
    return {
      status: 'rate_limited',
      retryAfter: response.headers.get('Retry-After')
    };
  }

  if (!response.ok) {
    const errorBody = await response.text();
    throw new Error(`Keyso API error ${response.status}: ${errorBody}`);
  }

  const data = await response.json();

  return {
    currentPage: data.current_page,
    lastPage: data.last_page,
    total: data.total,
    items: (data.data || []).map(row => ({
      source: 'keyso',
      domain,
      rawUrl: row.url,
      query: row.word
    }))
  };
}

5.6. Пример функции получения всех страниц пагинации

async function fetchAllKeysoUrlQueryPairs({ token, domain, base = 'msk' }) {
  const result = [];
  let page = 1;
  let lastPage = 1;

  do {
    const batch = await fetchKeysoSitePagesWithKeys({
      token,
      domain,
      base,
      page,
      perPage: 100
    });

    if (batch.status === 'pending') {
      await wait(10000);
      continue;
    }

    if (batch.status === 'rate_limited') {
      await wait(Number(batch.retryAfter || 60) * 1000);
      continue;
    }

    result.push(...batch.items);
    lastPage = batch.lastPage || page;
    page += 1;
  } while (page <= lastPage);

  return result;
}

5.8. Что не делать в MVP

В MVP не использовать как обязательные метрики позиции, частотность, видимость, трафик, историю изменений и расширенные SEO-поля. Их можно сохранить в raw_payload для будущего расширения, но текущая логика модуля анализа структуры должна опираться только на пару URL конкурента + Запрос.

6. Источник №2 — sitemap.xml

Sitemap используется как источник опубликованной структуры сайта. Для каждого конкурента система должна сначала проверить robots.txt, затем стандартные варианты: /sitemap.xml, /sitemap_index.xml, /sitemap-index.xml, /sitemap1.xml, /sitemap-catalog.xml, /sitemap_categories.xml, /sitemap-tags.xml, /sitemap.xml.gz.

Если найден sitemap index, нужно обработать вложенные карты. Система должна различать sitemap категорий, товаров, тегов, брендов, статей, изображений и новостей.

Если sitemap содержит в основном товары, он не считается полноценным источником структуры и получает частичный балл. Товары не включаются в основную структуру, но могут использоваться как дополнительный сигнал для брендов.

7. Источник №3 — мега-меню

Мега-меню запускается вручную массово или по конкретному конкуренту, если Keyso/sitemap дали недостаточно данных. Основной способ — извлечение DOM-ссылок из header/nav/menu. Резервный способ — скриншоты раскрытых меню и ИИ-анализ изображения.

  1. Открыть сайт в эмулируемом браузере.
  2. Определить блоки навигации и каталога.
  3. Раскрыть меню через hover/click/focus.
  4. Извлечь DOM-ссылки.
  5. Сделать скриншоты раскрытых состояний, если DOM недостаточен.
  6. Передать скриншоты ИИ.
  7. Получить список пунктов, URL, родителей, уровней и типов сущностей.
  8. Сохранить source = mega_menu_dom или mega_menu_screenshot.
8. Источник №4 — ручной импорт CSV/XLSX

SEO-специалист может импортировать структуру в формате CSV или XLSX. Обязательные столбцы: URL и Страница.

После загрузки система читает файл, проверяет обязательные столбцы, нормализует URL, извлекает сущности из названий страниц, присваивает source = manual_import, добавляет строки в общий пул и запускает тот же pipeline: фильтрация → классификация → дедупликация → группировка → сравнение.

Импорт не должен перезаписывать существующую структуру. Если сущность совпала с уже найденной, manual_import добавляется как дополнительный источник подтверждения.

9. Нормализация URL и черный список

Все URL проходят техническую нормализацию: убрать http/https, www, якоря, UTM, сортировки, параметры пагинации, привести trailing slash и регистр домена к единому виду.

Черный список исключает технические URL: /cart/, /basket/, /compare/, /search/, /personal/, /order/, /checkout/, /delivery/, /payment/, /contacts/, /vacancy/, ?sort=, ?utm_, ?PAGEN_ и т.д.

Исключенные элементы не удаляются физически, а сохраняются в excluded_items с raw_url, normalized_url, source, competitor, detected_type, exclude_reason и created_at.

10. Разделение URL и смысловой сущности

Система должна хранить четыре уровня данных: сырой URL, извлеченная сущность, нормализованная страница и рекомендованная страница для продвигаемого сайта.

Пример: raw URL /catalog/granit/slaby/ → извлеченная сущность “Слэбы из гранита” → нормализованная страница “Гранитные слэбы” → рекомендованная страница с типом, родителем, URL и статусом.

Дедупликация выполняется по смыслу, а не по URL.

11. Классификация страниц

Каждый URL или элемент меню должен получить тип: главная категория, подкатегория, теговая страница, фильтр, брендовая страница, бренд+категория, услуга, статья, товар, служебная страница, мусор.

Для структуры особенно важны категории, подкатегории, коммерческие теги, бренды, бренд+категория, сценарии применения, характеристики и статьи, если включен инфораздел.

12. Нормализация и удаление дублей

Конкуренты могут называть одно и то же по-разному. Например: “Гранитные слэбы”, “Слэбы из гранита”, “Плиты из гранита”, “Гранит в слэбах”. Система должна привести такие элементы к одному каноническому названию.

Уровни дедупликации: техническая дедупликация URL, текстовая нормализация, семантическая дедупликация ИИ, ручная премодерация.

ИИ должен определять полный дубль, частичный дубль, родительскую/дочернюю сущность, разные сущности, фильтр без посадочной, мусор и ручную проверку.

13. Модель статусов

Все найденные элементы по умолчанию получают статус “Кандидат”. Финальные статусы: создать, есть на сайте, объединить, сделать дочерней страницей, сделать тегом, сделать фильтром, оставить фильтром, не создавать сейчас, исключить, ручная проверка, отклонено клиентом.

Есть на сайте означает только факт найденного аналога на продвигаемом сайте, а не качество оптимизации страницы.

Для элементов со статусом “ручная проверка” должен быть доступен select для изменения статуса. После изменения обновляются таблица, дерево, счетчики и история изменений.

14. Расчет полноты и уверенности ИИ

Полнота конкурента: (keyso_score + sitemap_score + menu_score) × coverage_factor. Keyso дает до 40 баллов, sitemap до 35, мега-меню до 25. Веса выбраны по силе источников: Keyso показывает SEO-видимые URL+запросы, sitemap показывает опубликованную структуру, меню дает навигационный добор.

Качество источника считается коэффициентом 0–1. Например: полноценный Keyso = 1.0, частичный = 0.3–0.6, нет данных = 0.

coverage_factor: 60+ элементов после фильтрации — 1.0; 30–59 — 0.85; 10–29 — 0.65; меньше 10 — 0.4.

Статусы полноты: 75–100 ОК, 50–74 средне, 20–49 недостаточно, 0–19 нет данных.

Уверенность ИИ: competitors_factor × 0.35 + source_factor × 0.25 + entity_clarity × 0.20 + hierarchy_clarity × 0.10 + conflict_score × 0.10.

15. Итоговая структура, фильтры и сравнение

Итоговая структура отображается таблицей и XMind-подобным деревом. Таблица содержит: страница, тип, уровень, группа, конкурентов, источники, уверенность, статус, рекомендуемый URL и действие.

Фильтр структуры по статусам должен показывать как минимум: создать, есть на сайте, ручная проверка. Фильтр применяется к таблице и дереву.

Вкладка “Сравнение” интегрирована в “Структуру”. Основная зона роста — “есть у конкурентов, но нет у нас”.

16. Гостевая ссылка и согласование клиентом

По гостевой ссылке клиент видит только дерево структуры и кнопку экспорта. Технические таблицы, промты и DEV скрыты.

Клиент может отклонять раздел, категорию, подкатегорию, тег или бренд. Отклоненный элемент получает client_status = rejected, визуально деактивируется, действие сохраняется с датой/временем.

После клиентского согласования SEO-специалист получает утвержденный вариант и может отправить структуру на внедрение или запустить генерацию URL/мета.

17. Кнопка “Экспортировать”

Кнопка экспортирует итоговую таблицу структуры, чтобы было понятно, какая категория в каком разделе лежит, какие элементы являются тегами, фильтрами, брендами и т.д.

Минимальные колонки экспорта: ID, Parent ID, Level, раздел/родитель, страница, тип сущности, группа, рекомендуемый URL, H1, Title, Description, статус, источники, конкурентов, примеры URL конкурентов, уверенность ИИ, комментарий, статус клиента, комментарий клиента.

Приоритетный формат — XLSX; дополнительно можно поддержать CSV. Исключенные элементы по умолчанию не экспортировать, если нет отдельной настройки.

18. Кнопка “Сгенерировать URL и мета-теги”

Кнопка запускает финальный этап после обработки и согласования структуры. Источник генерации — согласованное дерево из раздела “Структура” с учетом решений SEO-специалиста и клиента.

Генерировать нужно URL, H1, Title и Description для активных элементов со статусами: создать, сделать тегом, сделать дочерней страницей. Для статуса “есть на сайте” по умолчанию не генерировать, чтобы не перезаписывать существующие страницы.

Перед генерацией должно открываться модальное окно с шаблонами URL, H1, Title, Description, переключателем “перегенерировать для существующих” и спойлерами с редактируемыми промтами.

У каждого промта в модальном окне должны быть кнопки: редактировать, сохранить, сохранить и запустить генерацию, скопировать, сбросить.

19. Результат генерации URL и мета

После генерации система выводит таблицу: страница, тип, родитель, уровень, URL, H1, Title, Description, статус генерации, комментарий, действие.

Конфликтные строки должны получать статус manual_review. Примеры конфликтов: exact_duplicate, existing_url_conflict, too_similar, wrong_parent, invalid_slug, too_long.

20. Таблицы данных и ограничения MVP

Рекомендуемые сущности хранения: raw_urls, extracted_entities, normalized_entities, entity_sources, excluded_items, manual_decisions, guest_decisions.

Ограничения MVP: нет полного краулинга, нет оценки качества оптимизации существующих страниц, нет автоматического создания страниц на сайте, нет автоматической публикации мета-данных, нет расширенных Keyso-полей кроме URL+Запрос.

Главная цепочка: ввод проекта → получение конкурентов → сбор Keyso → сбор sitemap → оценка полноты → мега-меню при необходимости → ручной импорт → фильтрация → классификация → извлечение сущностей → дедупликация → группировка → сравнение с сайтом → статусы → гостевое согласование → генерация URL и мета.
